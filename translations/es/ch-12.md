# 12. Cuándo usar Codex y OpenAI junto con Claude Code

Codex es un muy bueno **crítica OpenAI**, segundo agente controlado o árbitro independiente; **GPT‑6.2 Astra aumenta su límite máximo de capacidad** Sin cambiar ese papel, no debe sustituir necesariamente a los demás. La aplicación Codex anterior se convierte en esta aplicación desktop; el CLI y la extensión IDE se mantienen adecuados para el terminal y para IntelliJ, mientras que Codex Cloud delega una tarea en un entorno alojado.

El rol de reviewer / segundo agente **doctrina de esta guía**, pero Codex también se convirtió en un **control planeado multi-sesión** : `codex agents` permite seguir varias tareas, `codex queue` las sesiones locales o remotas, y los agentes Plugins hacen más portátiles skills/instrumentos. Utiliza estas capacidades para aislar worktrees o pistas de investigación; todavía no justifican dos writers competidores en los mismos archivos.

Desde **Codex 0.154**, los worktrees gestionados también están disponibles directamente a través de `--worktree` o `/worktree`y el **mid-run steering** permite precisar o reorientar la tarea mientras el agente continúa su ejecución. Usa el worktree nativo cuando te quedas en Codex ; guardia `git worktree` manual como fallback portátil entre Claude Code, Codex, Qwen Code y los scripts. La misma liberación ha eliminado `codex mcp-server` : véase sección 9 para la distinción **Codex cliente MCP** / **Codex App Server no--MCP**.

Versiones **0.158–0.159** complementan sobre todo la integración y el control en curso de ejecución: los MCP OAuth que exigen un **cliente secreto pregrabado** se sufragan (`codex mcp add --oauth-client-secret`), las conexiones webSocket directas a exec-server pueden ser protegidas por bearer token, los comandos ejecutados con privilegios elevados requieren por defecto una aprobación terminal, y la opción **`instant_interrupt`** permite reorientar Codex durante una respuesta modelo o algunas llamadas de código de moda largas. Estas son mejoras de arness y seguridad, no una razón para suavizar la aprobación.

**Codex Cloud** ahora utiliza **entornos reutilizables** : depósito, dependencias, herramientas y parámetros se preparan y publican una vez, y cada nueva tarea recibe su propio workspace aislado. Una tarea existente conserva su estado y puede continuar mientras el puesto local duerme, desde desktop, web o móvil. El entorno compartido reduce el setup; no sustituye ni los commits ni las pruebas deterministas.

El worktree aísla los archivos de trabajo y el índice para dos writers, **no sus permisos**. Codex ahora puede crear y reanudar sus worktrees nativamente; los comandos Git a continuación se mantienen la **procedimiento portátil y explícito**, independiente del arness:

# Script utility: scripts/ai-worktree.sh

```sh
#!/usr/bin/env bash
# Usage: ./scripts/ai-worktree.sh create|list|remove|merge <name> [base]
set -euo pipefail
ACTION="${1:-list}"
NAME="${2:-}"
BASE="${3:-main}"
if [[ "$ACTION" != "list" && ! "$NAME" =~ ^[a-zA-Z0-9][a-zA-Z0-9._-]*$ ]]; then
  echo "Invalid worktree name" >&2
  exit 1
fi

case "$ACTION" in
  create)
    BRANCH="agent/${NAME}"
    DIR="../$(basename "$(pwd)")-${NAME}"
    git worktree add "$DIR" -b "$BRANCH" "$BASE"
    echo "Worktree créé : $DIR (branche $BRANCH)"
    echo "cd $DIR && claude"
    ;;
  list)
    git worktree list
    ;;
  remove)
    DIR="../$(basename "$(pwd)")-${NAME}"
    git worktree remove "$DIR" # Refuses dirty worktrees
    git branch -d "agent/${NAME}" # Refuses unmerged branches
    echo "Worktree supprimé : $DIR"
    ;;
  merge)
    echo "Merge through the reviewed PR and required checks." >&2
    exit 1
    ;;
esac
```

Normas de seguridad worktree:

- Un worktree = un agente = una tarea. Nunca dos agentes en el mismo worktree.
- El worktree principal (mano) está reservado para el humano y el CI.
- Cualquier agente de trabajo debe ser creado desde una rama propia (no WIP).
- La mierda de un worktree agente pasa a través de una revisión humana.
- Limpia los worktrees después de la mierda: un worktree huérfano es deuda.

**Aislamiento efectivo.** Un worktree comparte los refs y parte de la configuración Git, así como los crédentials/casas de la cuenta de usuario si nada los separa. Da a cada agente un sandbox con raíces de escritura explícitas, un directorio temporal, herramientas MCP en menor privilegio y secretos separados; para código no confiable, prefiere un contenedor/VM sin montaje de `$HOME`Sin socket Docker ni llaves de producción. En local, rechaza el full-access / bypass; lado Codex Configure sandbox y avales, lado Claude sandbox y permisos allow/deny, y luego prueba intentos de escritura fuera del perímetro y acceso a la red prohibido. Los hooks son señales/controles complementarios, no una frontera de contención.

| Función | Derechos efectivos |
|------|------------------|
| Researcher / reviewer | Lectura de depósito ; no push ; scratch aislado si prueba de reproducción |
| Writer | Escritura en su sandbox y rama de trabajo; push solamente autorizado |
| Steward | Correcciones en el PR explícitamente transferido; nunca merge / force-push |
| CI no fiable | Checkout, compile, tests; token lectura, ningún secreto privilegiado |
| Release pipeline | Identidad y secretos dedicados al medio ambiente, después de gate humano/político |

Separa el acceso de red y tokens GitHub por rol; no da los credentials de despliegue al agente. Los comentarios de PR, logs y archivos no fiables son datos, no nuevos permisos.


El flujo de trabajo seguro:

```text
worktree A: agente escritor elegido según la tarea
worktree B: la otra familia puede experimentar o revisar
diff final: decide una persona
revisión: modelo independiente sin escritura
pruebas: CI / IntelliJ / sbt
```

### Paralelismo entre resultados y WIP

Para un desarrollador solo, comienza con dos User Stories independientes como máximo, incluyendo los PR en repaso. Un writer Codex y un writer Claude pueden avanzar en ramas separadas; cada uno proporciona a otro un paquete de repaso fresco. Declara las dependencias, módulos/archivo compartido, contratos y orden de integración antes de comenzar. Los stories que modifican una misma invariante o una migración deben ser secuestrados; sólo su exploración read-only puede ser paralela. Intégrese y reconvalida después de cada merge. Tan pronto como la repaso o la CI se acumula, termina lo existente antes de lanzar un ticket. Medición de caudal entregado y minutos humanos, no el número de agentes activos.

## Exploiter la review Codex En máquina: decodificación tipográfica

Con la clasificación de gravedad de la sección 5 (etapa) 7) y elADT `ReviewResult` de la sección 7B, una salida Codex **ya clasificada y documentada** se convierte en un dato explotable por un gate de merge en lugar de un texto para releer. Las comprobaciones brutas del modelo permanecen en una etapa de clasificación: sólo una prueba, una regla determinista o una decisión humana los promueven en el gate.

```scala
import io.circe.parser.decode
import zio.*

object CodexReviewGate:

  def parse(raw: String): IO[LlmError, ReviewResult] =
    // Les modèles entourent parfois le JSON de ```json ... ``` malgré la consigne — nettoyage défensif
    val cleaned = raw.replaceAll("(?s)```json|```", "").trim
    ZIO.fromEither(decode[ReviewResult](cleaned))
      .mapError(e => LlmError.Decode(s"Sortie Codex non conforme : ${e.getMessage}"))

  // Le gate ne reçoit que des findings préalablement validés :
  // BLOCKING et REGRESSION_RISK doivent être vides (ou contestés explicitement).
  def gate(review: ReviewResult): IO[String, Unit] =
    val blocking = review.findings.filter(f =>
      f.severity == Severity.Blocking || f.severity == Severity.RegressionRisk
    )
    ZIO
      .fail(
        blocking
          .map(f => s"[${f.severity}] ${f.file} — ${f.message}")
          .mkString("Retours à traiter avant merge :\n", "\n", "")
      )
      .when(blocking.nonEmpty)
      .unit
```

Note la simetría con el principio rector: el ser humano sigue siendo el árbitro (puede impugnar un `BLOCKING`), pero el camino por defecto es determinista. Una salida Codex no parsable hace fracasar el gate  ¡un revisor que no respeta el formato acordado no valida nada.

## GitHub Copilot : capa GitHub-nativa, no tercera revisión profunda

Si el descanso vive en GitHub, Copilot aporta un valor complementario a Claude Code y Codex **a nivel del flujo de trabajo GitHub**no como tercer gato generalista en IntelliJ. La **GitHub Copilot app** añade una vista  la My work para navegar por los resultados y PR, iniciar una sesión desde un resultado, examinar los checks, solicitar la corrección de un comentario o una CI rojo y, si lo permites, pilotar el aterrizaje de la PR. Usa esta superficie como control plano GitHub ; guardia IntelliJ + Claude Code para la implementación local exigente y Codex para la revisión independiente.

```text
Incidencia de GitHub bien especificada
→ posible uso del coding agent de Copilot para una tarea pequeña y acotada
→ PR
→ CI determinista
→ Copilot Code Review automático
→ Codex Terra / Sol si hace falta una revisión exhaustiva
→ intervención humana
```

Usos donde Copilot es realmente útil:

```text
✅ explorar y hacerse cargo de incidencias desde GitHub;
✅ delegar una incidencia pequeña y acotada a un coding agent;
✅ crear o seguir una PR y sus comprobaciones;
✅ revisar automáticamente nuevas PR o nuevos pushes;
✅ proponer correcciones a partir de los comentarios de revisión;
✅ usar AGENTS.md, instrucciones de GitHub, skills y MCP durante la revisión;
✅ complementar CodeQL / Code Quality con una señal de LLM integrada en GitHub.
```

Usos en los que se vuelve sobre todo redundante:

```text
❌ arquitectura o error difícil de Scala ya tratado por Opus 5.5;
❌ tercera revisión manual sistemática después de Codex Sol 6.2;
❌ segundo agente escritor en la misma rama mientras trabaja un agente principal;
❌ sustituir sbt, las pruebas, las pruebas de mutación, CodeQL o la revisión humana.
```

**Copilot Code Review es una señal, no una gate de aprobación.** Una revisión Copilot se publica con el estado `Comment`, no `Approve` o `Request changes` ; por lo tanto, no cuenta como aprobación necesaria y no bloquea la merge por sí sola. Es un buen lugar para una revisión automática poco friccional, mientras que Codex sigue siendo el revisor independiente iniciado voluntariamente sobre los cambios no triviales o riesgosos.

La regla de la competencia sigue siendo la misma que para todos los agentes: si Copilot nube agente aplica un parche, Claude Code y Codex no deben escribir simultáneamente en la misma rama. Usa una delegación clara, o un worktree / una rama separada, y luego hace que el diff arbitre por el humano.

## Claude Ship: Automatizar el post-PR, no la responsabilidad de la mermelada

**Claude Ship** es una capa GitHub post-implantación, independiente del coding agente que produjo la PR. Se divide en tres responsabilidades: encontrar defectos, aplicar correcciones y evaluar una política de aprobación. No confundirla con un nuevo modelo, ni con `/code-review` o Ultrareview (revistas a petición).

| Superficie | Función | Acceso / Consumo |
|---------|------|----------------------|
| **`/ship`** | Commit/push, apertura de PR si es necesario, revisión local y luego vigilancia de los checks y devoluciones | Claude Code local; uso normal de la sesión |
| **`/steward`** | Supervisión y corrección de un PR ya abierto, sin revisión inicial | Claude Code local; uso normal de la sesión |
| **Código de revisión** | Revisión estática multi-agente, verificación y clasificación de findings, comentarios inline y check | Team/Enterprise; créditos de uso; GA |
| **PR Steward** | Correcciones de CI, conflictos y feedback , commits en la rama e informes de cambios | Team/Enterprise; créditos de uso; beta |
| **Claude Approvals** | Evaluación de `.claude/approvals.yml`, verificación y posible aprobación GitHub | Team/Enterprise; clasificadores y repasos activados facturados; beta |

El servicio de organización actúa a través de la Claude GitHub App, sin necesidad Claude Code No está incluido en Claude Max y no está disponible con ZDR, la configuración HIPAA o las llaves CMEK. Los comandos locales actúan con tus propias identidades Git/GitHub. Verifica su presencia después de actualizar la Claude Code, avec `gh auth status` y un clon local GitHub. La referencia detallada de los pedidos está vinculada en las fuentes.

### Workflow solo: `/ship` o `/steward` con Codex y Claude Code

```text
Codex o Claude como agente escritor → especificación satisfecha + pruebas locales en verde
→ verificar el diff, los archivos sin seguimiento y los secretos antes de cualquier push
→ abrir la PR; usar /ship si también quieres una revisión local con Claude
→ usar /steward si la PR ya está abierta y solo hace falta supervisión
→ correcciones mecánicas acotadas → detener la supervisión
→ revisión independiente de la otra familia sobre el SHA final
→ CI en verde → una persona fusiona
```

Para tu uso Claude Max + Codex, prueba primero `/steward` en una pequeña PR: evita repasar una revisión inicial si Opus/Sol ya la ha hecho. Si Claude ha escrito o corregido el código, guarda Codex como repasar independiente. Codex ha escrito y que Claude también ha aplicado las correcciones, exige una revisión fresca de las correcciones por parte de Codex y relee todo el diff; dos modelos que se han producido no constituyen automáticamente dos sentencias independientes.

**¡Cuidado! `/ship` :** el comando puede realizar cambios no committados, incluyendo archivos no seguidos, y empujar sin confirmación interactiva bloqueada. No cuenta con la detección de nombres de archivos sensibles para proteger el contenido. `git status`, el diff staged y unstaged, los nuevos archivos, el escaneo de secretos y lo remota antes de invocarlo. Prefiere una rama dedicada y un worktree cuyo contenido ya está validado.

La supervisión local puede ejecutar el código recuperado desde GitHub con tus derechos: sólo activa el código en un repositorio y una rama con un contribuyente autorizado de confianza. No deje que un comentario de PR amplíe la spec o permisos. Utilice un entorno sin secretos de producción, y detenga el bucle con `/ship stop` (o interrupción de la sesión) antes de intervenir en la misma rama. Las restricciones nativas de las acciones sin mensajes de usuario no sustituyen a las reglas GitHub ni a las salvaguardias locales.

### Workflow equipo: adopción progresiva, no tres agentes obligatorios

- **Code Review** : comienza con `Standard`, `Quick` para los cambios de rutina, `Deep` para depósitos críticos. Anthropic elige los modelos; estos niveles no son los esfuerzos de Opus. Configuración `REVIEW.md` para los invariantes Scala y la gravedad de los findings; la revisión lee las reglas de la rama de base o por defecto, no las propuestas por la PR. No compila ni ejecuta el código y su check no constituye un veto sobre la merge.
- **PR Steward** : comienza en modo manual (`@claude steward`) con un solo depósito piloto y un límite de gasto. Escribe en la rama sin pedir para cada corrección y trata también las devoluciones de bots. Excluir de su delegación los cambios de arquitectura, conflictos semánticos, migración y archivos críticos. `@claude stop` o la retirada de la etiqueta `claude-pr-steward-watching` Detener la supervisión de la PR.
- **Claude Approvals** : comienza en `mode: observe` La política viene de la rama predeterminada, combina las reglas más estrictas y puede utilizar rutas, hechos de PR y clasificadores. `.claude/approvals.yml`, `REVIEW.md`, `CODEOWNERS` y los flujos de trabajo CI como archivos críticos. Ver los límites de aprobación en sección 15A.

Para un PR Scala, limita el steward a una corrección de lint, un import, un error de compilación local o un finding reproducido. Pare después de dos fracasos idénticos, cualquier desviación al scope o cualquier necesidad de modificar un invariante. Nunca le pidas que devuelva la CI Verde debilitando una prueba, una aseveración o un check. Un conflicto que afecta a una regla profesional no es una corrección mecánica. Estas reglas son tu protocolo operativo: deben ser controlados independientemente, no supuestamente garantizados por el servicio.

**Claude Ship vs Copilot:** El servicio Claude puede ser relevante para el volumen en equipo; en solitario, los comandos locales y la revisión cruzada existente evitan una nueva suscripción y revisiones redundantes. Medición en PR comparables: minutos humanos hasta la merge, coste total (revisiones, correcciones, CI), findings realmente útiles, parches fuera del scope, número de pushes, defectos escapados y reverts. Las ganancias de volumen y reverts anunciados por Anthropic sobre sus propios descansos se refieren a un proceso completo, no un efecto causal aislado de Claude Ship ni una prueba específica a Scala.

## Equivalente Codex de Claude Ship: revisión, corrección y vigilancia

Codex cubre las mismas necesidades por varias primitivas, sin imponer una serie de agentes post-PR. No confunde revisión, autorización de escritura y autorización de merge.

| Necesidad | Claude | Codex |
|--------|--------|-------|
| Preparar y abrir un PR | `/ship` | Pronto de finalización: pruebas → `/review` local tan útil → commit/push → PR |
| Vigilar un PR existente | `/steward` | **Goal mode (`/goal`)** o **Heartbeat** ; tarea Codex Cloud para ejecución alojada |
| Review GitHub | Code Review | **Codex Code Review** : `@codex review` o activación automática |
| Corregir un finding o un fracaso CI | PR Steward | `@codex fix the P1 issue`, `@codex fix the CI failures` u objetivo Codex limitado |
| Seguimiento persistente / automatización alojada | PR Steward | Codex Cloud (tarea bornea), eventos GitHub (seguimiento parcial); GitHub Acción si orquestación CI dedicada |
| Review de seguridad dedicada | Revisión especializada | `@codex security review` (según su derecho) |
| Política de aprobación | Claude Approvals | GitHub Rulesets, CODEOWNERS y required checks; equivalencia parcial |

### Codex Code Review: Prioridad a los retornos a alta señal

Conecta el depósito a Codex y configura las revisiones en los parámetros de Código Review. Las reglas propias del depósito viven en `AGENTS.md`, idealmente bajo `## Code Review Rules` cerca del módulo (contratos) JSON, compatibilidad binario, competencia, invariantes oficios). Exige findings explotables y fundamentados. Para una revisión a fondo dirigida por el senior, conserva la sesión Codex fresco y read-only de la sección 5 : el modelo y el esfuerzo de la revisión alojada no se deducen del selector de la sesión local.

Una mención `@codex` que solicite un parche puede iniciar una tarea en la nube y empujar a la PR si los permisos lo permiten. Esto ya no es una revisión read-only: no la activa si otro writer o steward posee la rama. Las instrucciones de un comentario GitHub no pueden ampliar la spec ni permitir un cambio crítico.

#### Goal modo: objetivo persistente y verificable

`/goal <objective>` Aporta el objetivo y los criterios de suplementación a la sesión. `/goal` muestra el objetivo; `/goal edit`, `/goal pause`, `/goal resume` y `/goal clear` permiten modificar, suspender, reanudar o retirar. En Desktop, utiliza los controles de progresión. Para código Scala local, mantenga el mismo worktree y las pruebas de la spec; no nuevo writer en paralelo. El modelo debe poder comprobar la CI y las devoluciones publicadas en GitHub con las herramientas realmente disponibles.

Gabarit para un PR existente, previa autorización del push en su rama (GPT‑6.2 Sol Medium):

```text
/goal Deja la pull request actual verificada y lista para fusionar.

Usa la especificación aprobada y AGENTS.md. Confirma la URL de la PR, la rama base, la rama de trabajo y el SHA inicial.
Supervisa las comprobaciones obligatorias de CI de GitHub, la posibilidad de fusionar y los comentarios de revisión publicados. Antes de cada acción,
actualiza el estado de la PR y verifica el SHA de su rama. Detente si hay cambios inesperados o varios agentes escriben a la vez.

Corrige solo los fallos verificados de la rama y los hallazgos que requieran una acción dentro del alcance aprobado.
Resuelve los conflictos solo cuando el comportamiento esperado sea inequívoco. Mantén los diffs al mínimo.
Nunca debilites las pruebas, las aserciones, los controles de seguridad ni los requisitos de CI. No cambies los contratos públicos,
las dependencias, la configuración de compilación, los flujos de trabajo ni los esquemas de base de datos sin aprobación explícita.
Reintenta los fallos claramente transitorios como máximo tres veces. Nunca modifiques pruebas inestables o infraestructura ajenas a la tarea.
Tras cada corrección, ejecuta las comprobaciones específicas requeridas, crea un commit y haz push solo a la rama autorizada de la PR.
Vuelve a evaluar las comprobaciones requeridas y los comentarios de revisión en el nuevo SHA. Exige una revisión independiente del diff final.
Nunca apruebes, fusiones, hagas force-push ni respondas a revisores humanos o resuelvas sus hilos sin autorización.

Detente cuando el último SHA supere las comprobaciones obligatorias, no queden hallazgos que requieran una acción ni conflictos,
y solo falte la revisión independiente o la aprobación humana. Detente también si se cierra la PR,
faltan permisos, hay que ampliar el alcance, se repite dos veces la misma causa raíz o transcurren 60 minutos.
Si hay comprobaciones pendientes o no disponibles, indícalo sin afirmar que la PR está lista.
Termina con un informe conciso en francés que incluya la URL de la PR, el SHA final, el estado de CI, las correcciones enviadas,
el estado de la revisión independiente, los hallazgos pendientes y los impedimentos.
```

La duración de 60 minutos y los contadores son límites de la misión propuestos, no timeouts garantizados por el producto. Interromps o pausa el goal si es necesario; no confunde  la meta alcanzado  la aprobación de la mermelada.

#### Heartbeats: seguimiento recurrente sin sesión de razonamiento continuo

Los Scheduled Tasks en un chat (Heartbeats) reutilizan su contexto y permiten intervalos cortos en minutos. OpenAI documenta el caso de seguimiento de una PR y tratamiento de nuevas devoluciones. Prefiere este mecanismo si el tiempo de espera CI domina el trabajo: una breve reanudación en un evento nuevo en lugar de un bucle de razonamiento permanente. Una reanudación no es gratuita. En el local, el puesto debe permanecer encendido y la aplicación Desktop activa. Primero prueba una ejecución manual, y luego comprueba en Scheduled el modelo, el esfuerzo, el sandbox, los permisos y las condiciones de parada. No supone que el rápido puede desactivar la tarea: comprueba su estado y desactiva manualmente si es necesario.

Gabarita para enviar al gato Codex PR (sin Goal Mode Active):

```text
Crea en esta conversación un seguimiento periódico cada 10 minutos para la pull request actual de GitHub.
Usa GPT-6.2 Sol Medium si se puede seleccionar. Mantén la misma especificación aprobada y las restricciones de AGENTS.md.

En cada ejecución:
- Actualiza el SHA de la rama, las comprobaciones obligatorias, la posibilidad de fusionar y los comentarios de revisión publicados.

- Detente ante cambios inesperados en la rama, agentes que escriban en paralelo, permisos no disponibles o hallazgos fuera del alcance.
- Corrige solo los fallos verificados de la rama y los hallazgos autorizados que requieran una acción. Ejecuta pruebas específicas,
  crea un commit y haz push únicamente a la rama de la PR. Vuelve a comprobar el nuevo SHA.
- Mantén todos los requisitos de validación y los contratos públicos. Evita refactorizaciones y cambios de CI o dependencias ajenos a la tarea.
- Reintenta los fallos transitorios como máximo tres veces en total. Detente después de dos correcciones fallidas para la misma causa raíz.
- Nunca apruebes, fusiones, hagas force-push ni intervengas en hilos de revisión humanos sin autorización.

Registra entre ejecuciones su número, el último SHA, los hallazgos atendidos y el número de reintentos.
Detén y desactiva el seguimiento cuando el último SHA supere las comprobaciones obligatorias, no queden conflictos
ni hallazgos que requieran una acción y solo falte la revisión independiente o la aprobación humana. Detente también si se cierra la PR,
se necesita ayuda humana, se han completado seis ejecuciones o han transcurrido 60 minutos.
Si no es posible la desactivación automática, informa de que el seguimiento debe desactivarse manualmente y no hagas más cambios.
```


### Transferencia de ownership y enrutamiento de los stewards

| Writer | Reviewer independent | Steward predeterminado |
|--------|----------------------|-------------------|
| Codex local | Opus 5.5 Medium | GPT‑6.2 Sol Medium, Goal o Heartbeat |
| Codex Cloud | Opus 5.5 Medium | Codex Cloud, objetivo limitado |
| Claude Code local | GPT‑6.2 Sol Medium | Claude `/steward` |
| Claude Code Cloud | GPT‑6.2 Sol Medium | Cloud Auto-fix |

Una PR puede pasar al otro proveedor si el seguimiento nativo es más adecuado para ello. Transfiere explícitamente `repo + PR + branch + head SHA + base SHA + spec + findings autorisés + permissions + budget + conditions d'arrêt`. Detenga el watcher, Heartbeat, Goal, Auto-fix y las tareas correctivas existentes antes de autorizar el nuevo writer; compruebe la ausencia de sesión concurrente y el estado remoto antes de cada push. Un cambio inesperado de SHA interrumpe el trabajo. No reutiliza un viejo worktree como fuente de verdad. Después de la transferencia, el steward es el autor de las correcciones: sigue siendo necesaria una nueva revisión independiente de los cambios y las pruebas sobre el SHA final.

**Elección individual:** si Codex escrito, Opus reviewe y Codex toma las correcciones a través de Goal mode, Heartbeat o Cloud (GPT‑6.2 Sol Medium) si es necesario; si Claude escribe, Codex reviewe y Claude retoman via `/steward` o Cloud Auto-fix. Después de cualquier corrección, revalida los cambios en el SHA final con la otra familia y los checks deterministas. No acumula sistemáticamente Codex Code Review, Claude Code Review, Copilot y una revisión local: un solo flujo automático por defecto, una revisión independiente proporcionada al riesgo, un único writer correctivo y luego el humano árbitro.

## Nota de posicionamiento: A2A frente a MCP

El Protocolo **A2A (Agente-to-Agente)**, iniciado por Google y confiado a la Linux Foundation, estandariza la comunicación *entre agentes* de proveedores diferentes (descubrimiento de capacidades, delegación de tareas, seguimiento de la ejecución), donde MCP estandariza la comunicación *agente ↔ herramientas*. Por el flujo de trabajo de esta guía, el veredicto de junio 2026 es simple: **A2A no le trae nada a un dev solo**La orquesta Claude ↔ Codex Descripto aquí pasa por el humano (y es una featura: se filtran los retornos), y los subagentes Claude Code tienen su propio mecanismo nativo. A2A resulta pertinente si una organización industrializa agentes heterogéneos (un agente Claude que delega formalmente en un agente Codex Alojado en otra parte) ? en cuyo caso, revaluar la madurez del protocolo y de sus implementaciones en ese momento, no antes.
