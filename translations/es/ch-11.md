# 11. Cuándo usar Aider y qué lugar ocupan OpenCode y Qwen Code

Aider sigue siendo útil, mantenido y muy eficaz para **par programming terminal orientado Git** : se le dan archivos precisos, produce parches legibles, y el historial Git Sigue siendo el undo stack.

OpenCode es un agente de código abierto más generalista, con terminal, IDE/desktop según configuración, múltiples sesiones e integraciones LSP/MCP. Para Scala, esto es interesante, pero hay que ser precisos: algunas capacidades LSP están todavía documentadas como experimentales o dependientes de un flag de configuración, y **Metals no forma parte de los LSP acid nativemente** - la solicitud de integración abierta en la presentación OpenCode (enero) 2026) se encuentra todavía en fase de debate a mediados de julio 2026. En la práctica, el feedback compilador Scala confiable en OpenCode pasa por un config LSP manual o por el **Metals MCP standalone** (sección 9), que sigue siendo la vía recomendada. Por lo tanto, no base una decisión de arquitectura de equipo únicamente en  ¡aOpenCode Pruebe en tu reposón, con Metalsy luego mide la calidad de los diffs.

Qwen Code es ahora más que un simple arness para Qwen : **Auto-Memory, Auto-Skills, suboficiales, MCPLSP, worktrees Git, modo headless y proveedores OpenAI/Anthropic/Qwen/local** Esto lo convierte en una alternativa de código abierto seria a Claude Code y Codex. Las versiones **0.24.x** refuerzan precisamente los puntos que importan para esta guía: cada `agent()` puede recibir una **allowlist explícito de herramientas**, los flujos de trabajo graban checkpoints y pueden ser reanudados o relanzados, los subagentes pueden ser aislados en contenedor, y el contexto inyectado por archivos/extensiones, así como el *tool surface* son mensurables y limitables. **0.24.7**, las herramientas retardadas pueden ser **lazy-loadés en Código de Modo** : `tools.eager` mantiene solamente los esquemas necesarios en la solicitud inicial, los demás
grabados y se descubren a través de `tool_search` → `tool_call`. La misma liberación añade una **memoria de llamada estructurada a petición** y continúa las sesiones/workspaces sostenibles. Es una implementación especialmente clara de `Select + Isolate` : elimina los esquemas innecesarios del prefijo sin perder la capacidad de llamar a la herramienta más tarde. La fundación de sandbox Linux se apoya ahora en `bwrap`. **Agente Equipo** y **Agente Arena** permanecen experimentales; Arena es especialmente útil para el benchmark privado, ya que varios modelos pueden recibir la misma tarea en worktrees aislados. `/advisor` proporciona un segundo dictamen independiente. La elección frente a OpenCode resto empírico: calidad de los parches Scala, estabilidad con Metals, coste total y calidad de la gestión de permisos. Local Control debe permanecer
limitada a una red local de confianza.

El buen reparto de los roles:

```text
Claude Code       = Opus 5.5/Sonnet 5.5 pour raisonnement, debugging et micro-dev
Codex             = Sol 6.2/Luna pour ownership d’issues et micro-dev OpenAI
OpenCode/QwenCode = harness pour Qwen local, modèles API et tâches parallèles isolées
Aider             = micro-diffs git-first quand tu veux un commit/petit patch par étape
```

> **Rappel**: no conecta tu suscripción Claude Max a OpenCode u otro arness de terceros. Para arneses de terceros,
> utilizar Qwen local o llaves API cumplen las condiciones del proveedor.

## Cuando se utilice Aider

Utilízalo para:

* pequeño parche objetivo;
* corrección de una prueba;
* renombrado local;
* migración mecánica simple;
* modificación en la que el diff Git es central;
* ciclo corto/prueba muy corto.

No lo utilice para:

* arquitectura;
* legacy gordo;
* Bugs de múltiples módulos;
* refactor profession profunda;
* decisión de diseño.

Aider es tanto mejor cuanto que respetas esta regla: ** añadir pocos archivos, dar una solicitud precisa, comprobar el diff, iniciar las pruebas selectivas**. Si añades demasiados archivos, recreas el problema que querías evitar: contexto costoso, atención diluido, diff más amplio.

Si esta disciplina te importa menos que el feedback LSP, OpenCode/Qwen Code pueden cubrir mejor los mismos casos, pero sólo después de la validación local en tu repo Scala.

## Comparativo sintético de los tres arneses

| Criterio                 | Aider                            | OpenCode                              | Qwen Code                             |
|-------------------------|----------------------------------|---------------------------------------|---------------------------------------|
| Filosofía             | Diff Git-first, mínimo          | Agente generalista, sesiones múltiples | Agente del ecosistema alineado Qwen          |
| Calidad de diff (Scala) | Muy buena en pequeño scope       | Variable para medir en tu repo     | Variable para medir en tu repo     |
| Soporte LSP/Metals      | No (repo map estático)          | Sí, parcialmente experimental.       | Sí; validar Metals en la repo      |
| MCP                     | No nativo                        | Sí.                                   | Sí.                                   |
| Local / BYOK            | Sí (todo compatible)   | Sí.                                   | Sí, óptimo con Qwen local          |
| Undo / rastreabilidad      | Excelente (un commit por paso) | Sesiones, menos Git-centrado            | Períodos de sesiones                              |
| Madurez Scala          | Probada en microdifs         | Prometida, no probada             | Harness maduro; calidad Scala a medir |

La columna decisiva no está en el cuadro: es **la calidad de los diffs en tu repo**, medida en diez tareas reales con la rejilla de métricas de la sección 3. El cuadro sirve para saber qué probar, no para decidir.

## Ejemplo: el comando de prueba que cualquier arness debe recibir

La palanca número uno de la hebilla lint/test es un comando común, reproducible y rápido. No deduzcas `FooSpec` del nombre `Foo.scala` : la continuación puede llevar otro nombre y un `testOnly` Sin pruebas seleccionadas puede tener éxito. En una CI limpio, `git diff HEAD` no ve los commits de la PR. Así que fija una **Base Git inmutable** y compararla con el candidato (merge base), teniendo en cuenta todos los estados Git para el feedback local.

Ejemplo `scripts/ai-validate.py` (Python) 3, Git, sbt ; adaptar `MODULES`, la política de caminos y los informes JUNIT al proyecto). Las suites listadas deben cubrir todos los módulos de prueba, incluyendo los módulos de integración; una suite sin prueba ejecutada requiere una configuración explícita, no un éxito silencioso.

```python
#!/usr/bin/env python3
"""Repository-specific example: adapt and protect the module map and policy."""
import argparse
import json
import re
import subprocess
import sys
import xml.etree.ElementTree as ET
from pathlib import Path

MODULES = {"api/": "api", "integration/": "integration"}
PROTECTED_NAMES = {"build.sbt", "plugins.sbt", "AGENTS.md", "CLAUDE.md", "CODEOWNERS", ".gitmodules"}
PROTECTED_DIRS = {".github", ".claude", ".codex", ".agents", "project", "migrations", "scripts"}
MAX_FILES, MAX_LINES = 20, 600


def git(*args):
    return subprocess.check_output(["git", *args])


def nul_paths(*args):
    return {p.decode("utf-8", "surrogateescape") for p in git(*args).split(b"\0") if p}


def changed_paths(base):
    # Union of committed, staged, unstaged and untracked paths; count renames as delete/add.
    return (nul_paths("diff", "--name-only", "-z", "--no-renames", base, "HEAD")
            | nul_paths("diff", "--cached", "--name-only", "-z", "--no-renames", base)
            | nul_paths("diff", "--name-only", "-z", "--no-renames", base)
            | nul_paths("ls-files", "--others", "--exclude-standard", "-z"))


def protected(path):
    parts = Path(path).parts
    return (bool(set(parts) & PROTECTED_DIRS) or Path(path).name in PROTECTED_NAMES
            or path.endswith(".sbt"))


def check_diff(base, head):
    # A final proof requires a committed candidate; never ignore untracked files.
    if git("status", "--porcelain=v1", "-z", "--untracked-files=all"):
        raise ValueError("Dirty candidate (including untracked files); inspect and commit authorized files first")
    raw = git("diff", "--raw", "-z", "--no-renames", base, head).split(b"\0")
    for metadata, raw_path in zip(raw[0:-1:2], raw[1:-1:2]):
        old_mode, new_mode = metadata[1:].split(b" ", 2)[:2]
        if {old_mode, new_mode} & {b"120000", b"160000"}:
            raise ValueError(f"Symlink or submodule requires separate review: {raw_path!r}")
    records = git("diff", "--numstat", "-z", "--no-renames", base, head).split(b"\0")
    count, lines = 0, 0
    for record in filter(None, records):
        added, removed, raw_path = record.split(b"\t", 2)
        path = raw_path.decode("utf-8", "surrogateescape")
        if protected(path):
            raise ValueError(f"Protected path requires separate human-approved policy: {path!r}")
        if added == b"-" or removed == b"-":
            raise ValueError(f"Binary change requires separate review: {path!r}")
        count += 1
        lines += int(added) + int(removed)
    if count > MAX_FILES or lines > MAX_LINES:
        raise ValueError(f"Diff exceeds policy: {count} files, {lines} lines")
    return {"files": count, "lines": lines}


def select_modules(paths):
    # Unknown/shared changes or no identified tests -> all declared test modules.
    if not paths or any(not any(p.startswith(prefix) for prefix in MODULES) for p in paths):
        return list(MODULES.values())
    return [module for prefix, module in MODULES.items()
            if any(path.startswith(prefix) for path in paths)]


def run_step(args, results):
    rc = subprocess.run(args, check=False).returncode
    results.append({"argv": args, "exit_code": rc})
    if rc:
        raise ValueError(f"Command failed ({rc}): {args!r}")


def verify_reports(prefix):
    # Adapt to actual report paths and frameworks; after clean, no stale reports.
    executed = 0
    for report in Path(prefix).glob("target/**/TEST-*.xml"):
        suite = ET.parse(report).getroot()
        if suite.tag != "testsuite":
            raise ValueError(f"Unexpected report format: {report}")
        if int(suite.get("failures", "0")) or int(suite.get("errors", "0")):
            raise ValueError(f"Failed tests in report: {report}")
        executed += int(suite.attrib["tests"]) - int(suite.get("skipped", "0"))
    if executed <= 0:
        raise ValueError(f"No executed tests proven for {prefix}")
    return executed


def main():
    parser = argparse.ArgumentParser()
    parser.add_argument("--base", required=True, help="Approved full Git commit SHA")
    parser.add_argument("--mode", choices=["targeted", "validate"], required=True)
    parser.add_argument("--sbt2", action="store_true")
    parser.add_argument("--receipt", type=Path, required=True)
    args = parser.parse_args()
    root = Path(git("rev-parse", "--show-toplevel").decode().strip()).resolve()
    receipt = args.receipt.resolve()
    if receipt == root or root in receipt.parents:
        parser.error("Receipt must be outside the repository")
    import os
    os.chdir(root)
    result = {"base": args.base, "mode": args.mode, "steps": [], "status": "FAILED"}
    try:
        if not re.fullmatch(r"[0-9a-f]{40}|[0-9a-f]{64}", args.base):
            raise ValueError("Expected a full immutable base SHA")
        head = git("rev-parse", "HEAD").decode().strip()
        base = git("merge-base", args.base, head).decode().strip()
        result.update(head=head, merge_base=base)
        if args.mode == "validate":
            result["diff"] = check_diff(base, head)
            modules = list(MODULES.values())
            # Full final validation, not a heuristic selection.
            run_step(["sbt", "scalafmtCheckAll", "compile", "Test/compile"], result["steps"])
        else:
            modules = select_modules(changed_paths(base))
        result["modules"] = modules
        test_task = "testFull" if args.sbt2 else "test"
        for prefix, module in MODULES.items():
            if module not in modules:
                continue
            # Explicit module suite: do not infer test names from source filenames.
            command = ["sbt", f"project {module}"]
            if args.mode == "validate":
                command.append("clean")
            run_step([*command, test_task], result["steps"])
            if args.mode == "validate":
                result.setdefault("executed_tests", {})[module] = verify_reports(prefix)
        if args.mode == "validate":
            if git("rev-parse", "HEAD").decode().strip() != head:
                raise ValueError("Candidate SHA changed during validation")
            check_diff(base, head)
            result["status"] = "PASSED"
        else:
            result["status"] = "FEEDBACK_ONLY"
    except (OSError, ValueError, subprocess.SubprocessError, ET.ParseError, KeyError) as exc:
        result["error"] = str(exc)
    finally:
        receipt.write_text(json.dumps(result, indent=2) + "\n", encoding="utf-8")
    print(json.dumps(result))
    return 0 if result["status"] in {"PASSED", "FEEDBACK_ONLY"} else 1


if __name__ == "__main__":
    sys.exit(main())
```

`--mode targeted` produce sólo feedback, aunque las pruebas son verdes. También inspecciona los archivos no seguidos y los cambios locales. Si no se identifica ningún módulo fiable, ejecuta todas las suites declaradas. En un edificio real, extiende la selección a los adictos impactados (por ejemplo, api → integración; el fallback sigue siendo todas las suites cuando el impacto es incierto. `--mode validate` requiere un candidato committado y un worktree limpio, controla el diff completo, ejecuta las suites completas después de `clean`, comprueba los informes de pruebas, el SHA y la limpieza final. Rechaza los caminos protegidos, binarios, symlinks y cambios de subsistema por defecto; toda excepción es una decisión humana en una política de validación separada y aprobada, nunca un argumento de bypass dado al writer.
`--sbt2` utilizar `testFull` en lugar de `test` para una ejecución completa en sbt 2.x. El script es un ejemplo de arness para adaptar y probar; el scope exacto de la spec y las excepciones deben ser comprobados por un humano o un allowlist de caminos aprobado independientemente. No cubre por sí solo todos los edificios Scala, los subcomponentes, las pruebas fuera de Junit o los archivos ignorados. CI debe ejecutar en un checkout aislado y limpio, con la política de confianza (sección 15A). No se confunde el informe JSON y certificado inviolable.

Wrapper `scripts/ai-test-changed` (ejecutable, compartido por Aider, Codex y Claude)

```bash
#!/usr/bin/env bash
set -euo pipefail
: "${AI_BASE_SHA:?Set the approved base commit SHA first}"
repoRoot=$(git rev-parse --show-toplevel)
receiptDir=$(mktemp -d)
printf 'Local feedback receipt: %s\n' "$receiptDir/validation.json"
exec python3 "$repoRoot/scripts/ai-validate.py" --base "$AI_BASE_SHA" \
  --mode targeted --receipt "$receiptDir/validation.json" "$@"
```

Al inicio, fija `AI_BASE_SHA` en la revisión aprobada (no a `HEAD` revalorada después de cada commit). Por ejemplo, en el worktree de tareas:

```bash
export AI_BASE_SHA="$(git rev-parse origin/main)"
aider --test-cmd "./scripts/ai-test-changed"
```

Antes de empujar la PR, en un candidato limpio y committado:

```bash
receiptDir=$(mktemp -d)
python3 scripts/ai-validate.py --base "$AI_BASE_SHA" --mode validate \
  --receipt "$receiptDir/validation.json"
```

Mantenga la prueba estructurada en el paquete de revisión (base, base de merge, SHA candidato, pedidos, códigos de devolución, número de pruebas ejecutadas y estado). Si la validación no está disponible, falla o se refiere a otro SHA, no declara "Done  ¡Done." Los propios scripts de validación requieren pruebas: salida sbt no cero sin `[error]`, untracked, commit ya creado, archivo renombrado a una ruta prohibida, informe ausente/vacío, SHA cambiado. Ejecuta estos casos en un repo temporal y un sbt Simulado antes de promover la política. Estos ejemplos fueron probados con un depósito Git temporaire et un sbt Simulado; esto valida la lógica de los scripts, no los comandos sbt Los checks end-to-end están pendientes de ejecución en CI.
