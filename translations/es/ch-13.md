# 13. Paquete mínimo de revisión para reducir las idas y venidas

Antes de pedir una revisión a Codex, Claude o un colega, siempre prepara un paquete corto:

```text
Ticket/spec :
Objectif :
Non-objectifs :
Fichiers modifiés :
Base SHA / merge base / PR head SHA :
Diff base → candidat + fichiers non suivis :
Exigences → preuves (commandes, résultats, rapports et SHA) :
Tests exécutés :
Tests non exécutés et pourquoi :
Risques résiduels :
Questions ouvertes :
```

No sólo da el diff. Una revisión sin spec produce comentarios genéricos; una revisión con objetivo, límites y pruebas produce más a menudo retornos activables. Proporciona primero el contrato y el diff sin las conclusiones del writer; las justificaciones vienen después del primer análisis independiente. El paquete debe ser regenerado cuando el SHA cambia.

> **¿Por qué este paquete no es opcional?** LinearB, *Software Engineering Benchmarks Report* (8,1 M+
> PRs, 4 800+ organizaciones), distingue PRs asistidos, PRs creados por agentes y PRs no asistidos.
> (esperanza antes de la primera toma) es aproximadamente 4,6 ¡más largo para los PRs asistidos; los PRs activos
> Aproximadamente 17,6 h frente a 3,4 h en el caso de las personas no asistidas 5,2–5,3
> pueden ser más grandes (408 líneas en contra 157 an 75La métrica de aceptación de LinearB
> es el **Porcentaje de PRs abiertos que se han metido en los 30 días** : 32,7 % para los PRs IA de la categoría
> publicado en contra de 84,4 % para los no subvencionados. No es ni una tasa de éxito de las pruebas ni una tasa de rechazo
> definitiva. No confunde las categorías: la desviación de pickup agente no es el número de PRs asistidos.
>
> Opera, *AI Coding Impact Benchmark Report* (250 000+ desarrolladores, 60■ las empresas), estudia las ganancias de
> velocidad de creación de los PRs y el desplazamiento del gulot hacia la revisión. DORA observa que la IA amplía los
> fundaciones existentes: las ganancias de flujo no implican una mejora automática de la estabilidad.
> Estos informes siguen siendo observadores , con diferentes definiciones y tareas; no demuestran
> Prioridad: PRs cortos, contrato explícito, WIP borné, prueba de validación
> y reducción del tiempo hasta la producción. El umbral 600 líneas / 20 archivos es un límite de alerta,
> no un objetivo de tamaño de PR.

En el caso de los PRs activos, deberá vigilarse especialmente:

```text
- nombre de fichiers modifiés ;
- taille du diff ;
- fichiers hors scope ;
- CI rouge ;
- tests ajoutés qui ne peuvent pas échouer ;
- refactor non demandé ;
- changement implicite de contrat public ou JSON ;
- modification de build sans validation.
```
