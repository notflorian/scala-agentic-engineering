## Para comprimir con RTK / Headroom

* logs CI;
* salidas `sbt test` largas;
* gordo `git diff` ;
* `rg` macizo;
* JSON voluminoso;
* documentación larga;
* Listings de archivos.

## No comprimir agresivamente

* Código fuente que debe modificarse;
* pruebas críticas;
* `build.sbt` ;
* migración;
* stack rastros Scala complejos;
* errores de implicits/givens;
* contratos JSON públicos.

Las cinco palancas de coste acumulables son: enrutamiento a modelos baratos, compacción del contexto, prompts scopées con rutas de archivo, prompt caching y Batch API cuando se adapta.

> **Context rot.** No confunde tres límites diferentes:
>
> ```text
> capacité physique     = combien de tokens entrent dans la fenêtre ;
> récupération          = le modèle retrouve-t-il encore l'information pertinente ;
> raisonnement utile    = sait-il encore l'appliquer correctement parmi tout le reste ?
> ```
>
> Literatura 2026 muestra que las dos últimas pueden degradarse gradualmente **Mucho antes** saturación
> física. A la misma tarea, añadir contexto innecesario puede reducir la calidad incluso cuando la información pertinente
> Los síntomas típicos de una larga sesión de agente son: limitaciones antiguas menos
> , reversiones de hipótesis ya refutadas, relectura repetida de los mismos archivos, hebillas de corrección y abandono
> a pesar de la información suficiente.
>
> Por lo tanto, una transcripción larga no es una mejor memoria. En una sesión de código también acumula `rg`, salidas
> MCP,
> El **working set decision** debe:
> permanecer pequeño:
>
> ```text
> objectif + contraintes + plan + décisions + diff courant + preuves essentielles
> ```
>
> La compaction (`/compact`) sigue siendo una compresión con pérdidas: se produce después de la acumulación y puede
> Resumiendo un invariante discreto, una hipótesis refutada o un detalle raro. **No la trate como un mecanismo normal de
> continuación.** Para una tarea importante, prefiere un handoff explícito y controlado (`HANDOFF.md` o archivo de estado,
> El desfile estructural sigue siendo el **aislamiento en la parte superior** : delegar la exploración voluminosa,
> logs, pruebas, documentación e investigaciones independientes a subagentes con su propio contexto,
> Y luego sólo saca conclusiones cortas y cegadas.
>
> ```text
> 100K tokens explorés dans un worker
> → 1–2K tokens de résultat
> → parent propre pour décider et écrire
> ```
>
> Esta norma también se aplica a la revisión: **no da a Codex la transcripción completa de una larga sesión Claude**.
> Dale una ventana fresca con `spec + diff final + fichiers modifiés + tests + invariants`. Tú consigues a la vez
> aislamiento de modelo y aislamiento de contexto.

Para la caché explícita OpenAI, razona en el costo total: una escritura para 1,25× sin ninguna reutilización cuesta más que una llamada normal. Con al menos una reutilización del mismo prefijo durante la vida útil del caché, una escritura y luego una lectura a 0,1× coste 1,35× en total contra 2× sin caché. Por lo tanto, activa un breakpoint sólo para un prefijo estable cuya reutilización es probable, y mide por separado tokens escritos, tokens leídos, tasa de hit e invalidaciones.

## Las cuatro estrategias canónicas del context engineering

La disciplina se formalizó fin 2025 bajo el nombre de **context engineering** Definición Anthropic: • todas las estrategias para curar y mantener el conjunto óptimo de tokens durante la inferencia • formulación Karpathy: • llenar la ventana de contexto con la información correcta para el siguiente paso • La taxonomía de referencia (LangChain) distingue cuatro estrategias, que esta guía práctica ya por separado • las nombra para comprobar que ninguna se olvida:

| Estrategia    | Pregunta                                      | Aplicación de esta guía                                                                                      |
|--------------|-----------------------------------------------------|------------------------------------------------------------------------------------------------------------------|
| **Write**    | ¿Qué tiene que sobrevivir fuera de la ventana?    | `AGENTS.md`, `MIGRATION_STATE.md`, auto-memory, registros de tareas, registro de deudas                            |
| **Select**   | ¿Qué entra en la ventana, y cuándo?     | Sourcebot / ScalaSemantic / Codebase-Memory / rg / Metals MCP, recuperación justo a tiempo                        |
| **Compress** | ¿Qué puede perder tokens sin señal?  | RTK / Headroom en logs y diffs, salidas truncadas, handoff estructurado; `/compact` sólo como último recurso |
| **Isolato**  | ¿Qué debe vivir en una ventana separada? | Subagents read-only, worktrees, reviewer no-write, sessions distinct por work                                 |

Dos normas operativas que se derivan de esta tabla y que el resto de la guía no abarca explícitamente:

- **Progressive disclosure of instruments** : cada servidor MCP añade sus esquemas de herramientas a la ventana de cada sesión. Limita los servidores y herramientas activados por agente (elACP d'IntelliJ y Claude Code lo permiten) y prefiere el descubrimiento a la demanda MCP de agosto 2026 por otra parte, la *progresivo discovery* catálogos de herramientas una prioridad del protocolo. En un catálogo grande, **Jev puede servir de pre-selector** : elegir algunos skills/instrumentos candidatos antes de cargar sus definiciones en el contexto del LLM.
- **Compasión como decisión, no como reflejo** : puntuación Jev puede informar `topic_shift` o `old_context_still_needed`, pero es el arness que decide luego compactar. Nunca dejes que la decisión modelo reescribir él mismo el historial; conserva las decisiones y artefactos duraderos en `HANDOFF.md` / `MIGRATION_STATE.md`.
- **Presupuesto de selección** : si un elemento de contexto no cambia ninguna decisión del paso actual, no pertenece a la ventana. Medir periódicamente la parte de los tokens que realmente han influido en la salida (tasa de caché hit, redundancia de los archivos inyectados): una ventana grande no es una excusa para un contexto no filtrado.

>
> **Qwen Code hace que este presupuesto sea ahora observable.** Las versiones 0.23.x muestran la parte del contexto consumido por el
> Sistema prompt, herramientas integradas, MCP, memoria, skills y mensajes. Las versiones 0.24.x añaden la atribución del
> costo
> en tokens a los archivos de contexto/extensiones, límites sobre grandes *tool superficies*, un allowlist de herramientas por
> subagente y la construcción del sistema prompt a partir del **resident tool set** realmente activo. Las herramientas retardadas
> pueden permanecer fuera del prefijo al mismo tiempo que se conserva el prompt caché. Utiliza estas métricas como auditoría empírica:
> **retirar o diferir un provider, una extensión o una herramienta que consume regularmente contexto sin modificar una
> Decisión**.

> **Cifras y cascadas para este presupuesto.** Los trabajos 2025-2026
> convergente sobre un objetivo de utilización de **~30–40 % de la ventana** en régimen normal (una ventana 200K apunta
> ~60–80K de contenido real, no 190K) : más allá, el *context rot* se instala incluso con la capacidad restante. Tres
> resultados concretos que se han de integrar:
> - **concebir las salidas de herramientas primero**: modos silenciosos, trompeta (por ejemplo > 2 000 tokens → escrito en
>   disco + preview de 10 líneas), campos operables en lugar de JSON en bruto. Esto amplía el contexto real de
>   ~3–4 ¡Sin ninguna infraestructura de compresión; resumen por LLM lo que una herramienta podría no haber emitido es
>   la versión de pago del mismo problema;
> - **Enmascaramiento de observación antes de resumir LLM** : un benchmark JetBrains en SWE-bench Verified muestra que
>   reemplazar los antiguos outputs de herramientas por placeholders (manteniendo el esqueleto acciones/raido)
>   reduce los costes de ~52 % sin prolongar las trayectorias, mientras que el resumen LLM puro (−50 % de coste) aumenta los
>   trayectorias de ~15 %. Las capas sin LLM tratan la mayoría de la presión; el resumen es el backstop caro;
> - ** Resúmenes estructurados de campos fijos** (intención, progreso, hechos clave, artefactos, próximos pasos, preguntas
>   Abiertos: golpean a la prosa libre, pero ** ningún enfoque preserva bien el rastro de los artefactos** (archivo
>   créés/modifiés) — d'où le fichier d'état maintenu hors du pipeline de compression, et la vigilance sur les
>   - resumen de resúmenes  - que pierden detalles de las primeras horas.
>
> Estas prácticas responden a los cuatro modos de fallo mencionados en la taxonomía de referencia: *context vensoning*
> (una alucinación referenciada en bucle), *context distraction* (el modelo supera el historial en detrimento de
> el objetivo), *context confusión* (del contenido superfluo degrada incluso sin saturación de casos canónicos , fracaso con
> 46 herramientas, éxito con 19, con la misma ventana) y *context clash* (una corrección coexiste con el error
> que sustituye, ~ −39 % de rendimiento). Estas son las causas fundamentales que las estrategias Write / Select / Compress /
> Isolate arriba neutralizan una por una.

> **Validación industrial, no benchmark controlado.** GitHub documentó la migración del runtime
> Copilot de TypeScript a **832 378 Líneas de Rust de producción**, entregada progresivamente en **128 PRs**. El regreso
> de experiencia **96,22 % de caché reads** sobre el volumen de tokens de entrada y **5 116 compactions** ; las
> subagentes
> Gastan su contexto en una ventana separada y luego sólo devuelven su respuesta al padre, mientras que los
> períodos de sesiones
> que escriben en paralelo disponen de su propia rama y worktree. Es una confirmación industrial muy fuerte
> de **prefijo estable + Isolate + map→ reduce + worktrees**, pero no una prueba causal general a todos los depósitos.
>
> El mismo retorno insiste en dos salvaguardias ya presentes aquí: los **Pruebas E2E debe seguir siendo un oráculo independiente
que
> el agente no puede reescribir silenciosamente**y la migración debe **traducir el comportamiento primero, rediseñe
> Luego**. Para una migración Scala/JVM, protege las pruebas de caracterización y los contratos antes de dar al
> writer
> permiso para modificar la implementación.

#### Árbol de decisión: continuar vs handoff + sesión fresca vs `/compact`

El error más costoso en créditos es continuar una sesión contaminada. Aquí está el árbol de decisión a aplicar todos los ~15 interacción o en cuanto aparezca un síntoma de context rot:

```text
Session en cours
│
├─ L'agent répète une hypothèse déjà réfutée ou accumule les erreurs ?
│  └─ OUI → STOP → HANDOFF.md vérifié → nouvelle session
│             (ne PAS changer seulement de modèle dans la conversation polluée)
│
├─ Le contexte contient > 50 % de tokens non décisionnels
│  (logs bruts, rg massif, anciennes versions du diff) ?
│  └─ OUI → écrire HANDOFF.md :
│             objectif, contraintes, plan, décisions, artefacts,
│             diff courant, preuves, erreurs non résolues, prochaine action
│           → relire le handoff
│           → nouvelle session avec ce working set minimal
│
├─ La tâche a changé de nature ?
│  (bugfix → refactor, feature → migration)
│  └─ OUI → nouveau cadrage complet (Étape 0) + nouvelle session
│
├─ Le modèle utilise encore correctement les invariants et non-objectifs ?
│  └─ NON → ré-injecter la charte si le contexte reste sain ;
│           sinon handoff + nouvelle session
│
└─ Aucune condition ci-dessus → continuer
```

`/compact` se convierte en el **plan B**, reservado a los casos en los que la superficie impone conservar la sesión. Antes de usarlo, haz que produzca y luego relee un handoff estructurado; después de compacción, comprueba explícitamente que los invariantes, decisiones, artefactos y errores abiertos sobrevivieron. Si falta un detalle crítico, abandona la sesión compactada.

Regla métrica: si el ratio (tokens en la ventana) / (tokens realmente citados o utilizados en 3 Últimas respuestas) supera 5:1, la sesión está sobrepeso. El defecto es **handoff + sesión fresca**, no más compresión.

## Ejemplo: estructurar una petición oculta en Scala 3

La disciplina de la sección 4 (estático en la parte superior, dinámico en la parte inferior) se traduce directamente en la construcción de la consulta. `cache_control` se cobran ~5 à 10 % de la tarifa input a partir de la segunda convocatoria (5 % de Sonnet 5.5 y Opus 5.5) Siempre que sea byte para byte idénticos entre las llamadas:

```scala
import io.circe.Json
import io.circe.syntax.*

object CacheablePrompt:

  // STATIQUE — chargé une fois au démarrage, jamais reconstruit dynamiquement :
  // toute interpolation (timestamp, compteur...) dans ces blocs casse le cache.
  def systemBlocks(agentsMd: String, scalaRules: String): Json =
    Json.arr(
      Json.obj(
        "type"          -> "text".asJson,
        "text"          -> agentsMd.asJson,
        "cache_control" -> Json.obj("type" -> "ephemeral".asJson)
      ),
      Json.obj(
        "type"          -> "text".asJson,
        "text"          -> scalaRules.asJson,
        "cache_control" -> Json.obj("type" -> "ephemeral".asJson)
      )
    )

  // DYNAMIQUE — change à chaque itération, va dans messages, jamais dans les blocs cachés
  def userMessage(diff: String, compileErrors: String): Json =
    Json.obj(
      "role"    -> "user".asJson,
      "content" -> s"Diff courant :\n$diff\n\nErreurs :\n$compileErrors".asJson
    )

  def request(agentsMd: String, scalaRules: String, diff: String, errors: String): Json =
    Json.obj(
      "model"      -> "claude-sonnet-5-5".asJson,
      "max_tokens" -> 4096.asJson,
      "system"     -> systemBlocks(agentsMd, scalaRules),
      "messages"   -> Json.arr(userMessage(diff, errors))
    )
```

Verifica la caché hit en la respuesta (`usage.cache_read_input_tokens > 0`) y loggelo: una tasa de caché hit que casi siempre se desploma indica un encabezado de prompt que se vuelve inestable. 4 de la sección
