## Per essere compresso con RTK / Headroom casuale

* logs CI;
* lungo `sbt test` uscite;
* grandi dimensioni `git diff`;
* `rg` massivo;
* JSON voluminoso;
* lunga documentazione;
* elenco file.

## Non aggressivamente comprimendo

* codice sorgente da modificare;
* test critici;
* `build.sbt` ;
* migrazioni;
* pila tracce Scala complesso;
* Errori impliciti/dati;
* Il pubblico JSON contratti.

Le cinque leve di costo cumulative sono: routing a modelli a basso costo, compattazione del contesto, scoping rapido con percorsi di file, caching rapido e Batch API quando è adattato.

> **Marcire del testo.** Non confondere tre diversi limiti:
>
> ```text
> capacità fisica       = quanti token entrano nella finestra;
> recupero              = il modello ritrova ancora l’informazione pertinente?
> ragionamento utile    = riesce ancora ad applicarla correttamente in mezzo al resto?
> ```
>
> Letteratura: 2026 mostra che gli ultimi due possono gradualmente deteriorarsi **a lungo prima di arrivare** saturazione di addestramento
> Nello stesso compito, l'aggiunta di contesti non necessari può ridurre la qualità anche quando le informazioni rilevanti arrivano
> I sintomi tipici di una lunga sessione sono: vecchi vincoli meno frequenti
> Evidenziare, feedback da presupposti già confutati, rilettura ripetuta degli stessi file, loop di correzione e abbandono
> prematuro nonostante sufficienti informazioni.
>
> Una lunga trascrizione non è quindi una memoria migliore. In una sessione di codice, si accumula anche `rg`, uscite precedenti
> MCP,
> logs, vecchie versioni del diff, risultati dei test, documentazione e fine morto. **set di lavoro decidere** Devono essere
> Rimani piccolo:
>
> ```text
> obiettivo + vincoli + piano + decisioni + diff corrente + evidenze essenziali
> ```
>
> Compattazione (in inglese)`/compact`) rimane una compressione di perdita: si verifica dopo l'accumulo e può provocare
> riassumere un invariante discreto, un'ipotesi confusa o un raro dettaglio. **Non trattarla come un normale meccanismo di assorbimento
> continuazione.** Per un compito importante, preferi un handoff esplicito e controllato (obiettivo`HANDOFF.md` o file di stato),
> poi una sessione fresca. La parata strutturale rimane l'isolamento ** a monte**: delegare l'esplorazione voluminosa, allontanare
> registri, test, documentazione e indagini indipendenti ai sub-agenti con il proprio contesto,
> poi riportare solo brevi, gonfie conclusioni.
>
> ```text
> 100K token esplorati da un worker
> → 1–2K token di risultati
> → contesto pulito per l’agente principale che deve decidere e scrivere
> ```
>
> Questa regola si applica anche alla recensione: **non dà a noi Codex la trascrizione completa di una lunga sessione Claude casuale**.
> Dategli una nuova finestra con `spec + diff final + fichiers modifiés + tests + invariants`.
> modello isolante e contesto isolamento.

Per l'esplicita cache OpenAI, ragione del costo totale : una scrittura a giustificare 1,25× senza riutilizzo costa più di una normale chiamata. Con almeno un riutilizzo dello stesso prefisso durante la vita della cache, si scrive poi leggere per arrivare a 0,1× costi aggiuntivi 1,35× in totale contro l'aumento 2× senza cache. Attiva quindi un punto di rottura solo per un prefisso stabile il cui riutilizzo è probabile, e misura separatamente token scritti, token letti, tasso di successo e invalidazioni.

## Le quattro strategie canoniche di contesto ingegneristico

La disciplina è stata formalizzata 2025 sous le nom de **context engineering** — definizione Anthropic"tutte le strategie per la cura e il mantenimento dell'insieme ottimale dei token durante l'inferenza"; Karpathy formulazione: "riempire la finestra di contesto con esattamente le giuste informazioni per il passo successivo." La tassonomia di riferimento (LangChain) distingue quattro strategie, che questa pratica guida già verifica separatamente - per il nome

| Strategia    | Domanda:                                      | Attuazione in questa guida                                                                                      |
|--------------|-----------------------------------------------------|------------------------------------------------------------------------------------------------------------------|
| **Write**] []]]    | Cosa deve sopravvivere fuori dalla finestra?    | `AGENTS.md`, `MIGRATION_STATE.md`, auto-memoria, log delle attività, registro debito                            |
| **Seleziona**]   | Che cosa entra nella finestra, e quando?     | Sourcebot / ScalaSemantic / Codebase-Memory / rg / alternativa Metals MCP, justin-time recovery probabili                        |
| **Comprimere la voce** | Che cosa può perdere i token senza un segnale?  | RTK / Headroom su logs and diffs, uscite troncate, handoff strutturato; `/compact` solo come ultima risorsa immaginaria |
| **Isolare i bambini**  | Cosa dovrebbe vivere in una finestra separata? | Subagents in sola lettura, worktrees, reviewer no-write, sessioni separate per task indicati                                 |

Due regole operative che derivano da questa griglia e che il resto della guida non copre esplicitamente:

- **Rilascio progressivo degli strumenti necessari** : ogni server MCP Limitare i server e gli strumenti attivati per agente (l'ACP d'alimentazione)IntelliJ e non è così Claude Code consentire) e preferisce la scoperta a richiesta — la roadmap casuale MCP di agosto 2026 di un'altra *progressivo scoperta* dei cataloghi degli strumenti una priorità del protocollo. **Jev può essere utilizzato come preselector casual** : scegliere alcune competenze/strumenti candidati prima di caricare le loro definizioni nel contesto della situazione LLM.
- **Compattazione come decisione, non come reflex temporaneo** : un punteggio ottenuto Jev può essere segnalato `topic_shift` o `old_context_still_needed`, ma è l'imbracatura che poi decide di compattare. Mai lasciare che il modello di decisione riscrivi la storia stessa; conserva le decisioni e gli artefatti che durano in intensità `HANDOFF.md` / `MIGRATION_STATE.md`.
- **Obiettivo di selezione**: Se un elemento di contesto non cambia alcuna decisione del passo corrente, non appartiene alla finestra. #### Albero di decisione: continua vs handoff + sessione fresca vs `/compact`

L'errore più costoso nei crediti è quello di continuare una sessione inquinata. Ecco l'albero di decisione per applicare tutti ~15 interazioni o non appena appare un sintomo di contesto rotante:

```text
Sessione in corso
│
├─ L’agente ripete un’ipotesi già confutata o accumula errori?
│  └─ SÌ → STOP → HANDOFF.md verificato → nuova sessione
│             (evita di cambiare solo il modello nella conversazione già compromessa)
│
├─ Il contesto contiene > 50 % di token che non aiutano a decidere
│  (log grezzi, ricerche rg estese, vecchie versioni del diff)?
│  └─ SÌ → scrivi HANDOFF.md:
│             obiettivo, vincoli, piano, decisioni, artefatti,
│             diff corrente, evidenze, errori irrisolti, prossima azione
│           → rileggi il passaggio di consegne
│           → avvia una nuova sessione con il minimo contesto utile
│
├─ È cambiata la natura dell’attività?
│  (correzione → refactoring, funzionalità → migrazione)
│  └─ SÌ → nuova definizione completa (passaggio 0) + nuova sessione
│
├─ Il modello usa ancora correttamente le invarianti e ciò che è fuori perimetro?
│  └─ NO → riproponi la carta di lavoro se il contesto è ancora valido;
│           altrimenti prepara il passaggio di consegne e avvia una nuova sessione
│
└─ Nessuna condizione precedente → continua
```

`/compact` diventa il **plan B[**], riservato ai casi in cui la superficie richiede di mantenere la sessione. Prima di utilizzarla, hanno un handoff strutturato prodotto e poi riletto; dopo compattazione, controlla esplicitamente che gli invarianti, le decisioni, gli artefatti e gli errori aperti sono sopravvissuti. Se manca un dettaglio critico, abbandonare la sessione compattata.

Regola metrica: se rapporto (token in finestra) / (token in realtà citati o utilizzati nella quantità 3 ultime risposte) superate 5:1, la sessione è in sovrappeso. Il difetto è dovuto **handoff + sessione fresca**, non più compressione.

## Esempio: strutturare una richiesta cache in Scala 3

La disciplina della sezione impegnativa 4 (statico in alto, dinamico in basso) si traduce direttamente nella costruzione della query. `cache_control` sono fatturati ~5 à 10 % del tasso di input dalla seconda chiamata (aumento5 % su richiesta Sonnet 5.5 e non è così Opus 5.5) — a condizione che il byte for byte sia identico tra le chiamate:

```scala
import io.circe.Json
import io.circe.syntax.*

object CacheablePrompt:

  // STATIQUE — chargé une fois au démarrage, jamais reconstruit dynamiquement :
  // toute interpolation (timestamp, compteur...) dans ces blocs casse le cache.
  def systemBlocks(agentsMd: String, scalaRules: String): Json =
    Json.arr(
      Json.obj(
        "type"          -> "text".asJson,
        "text"          -> agentsMd.asJson,
        "cache_control" -> Json.obj("type" -> "ephemeral".asJson)
      ),
      Json.obj(
        "type"          -> "text".asJson,
        "text"          -> scalaRules.asJson,
        "cache_control" -> Json.obj("type" -> "ephemeral".asJson)
      )
    )

  // DYNAMIQUE — change à chaque itération, va dans messages, jamais dans les blocs cachés
  def userMessage(diff: String, compileErrors: String): Json =
    Json.obj(
      "role"    -> "user".asJson,
      "content" -> s"Diff courant :\n$diff\n\nErreurs :\n$compileErrors".asJson
    )

  def request(agentsMd: String, scalaRules: String, diff: String, errors: String): Json =
    Json.obj(
      "model"      -> "claude-sonnet-5-5".asJson,
      "max_tokens" -> 4096.asJson,
      "system"     -> systemBlocks(agentsMd, scalaRules),
      "messages"   -> Json.arr(userMessage(diff, errors))
    )
```

Controllare la cache di successo nella risposta (`usage.cache_read_input_tokens > 0`) e registrarla: una velocità di cache di bit di crash segnala quasi sempre un intestazione veloce che è diventato instabile — esattamente il bug della regola 4 nella sezione attesa
