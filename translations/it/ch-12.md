# utilità script: scripts/ai-worktree.sh verifica

```sh
#!/usr/bin/env bash
# Usage: ./scripts/ai-worktree.sh create|list|remove|merge <name> [base]
set -euo pipefail
ACTION="${1:-list}"
NAME="${2:-}"
BASE="${3:-main}"
if [[ "$ACTION" != "list" && ! "$NAME" =~ ^[a-zA-Z0-9][a-zA-Z0-9._-]*$ ]]; then
  echo "Invalid worktree name" >&2
  exit 1
fi

case "$ACTION" in
  create)
    BRANCH="agent/${NAME}"
    DIR="../$(basename "$(pwd)")-${NAME}"
    git worktree add "$DIR" -b "$BRANCH" "$BASE"
    echo "Worktree créé : $DIR (branche $BRANCH)"
    echo "cd $DIR && claude"
    ;;
  list)
    git worktree list
    ;;
  remove)
    DIR="../$(basename "$(pwd)")-${NAME}"
    git worktree remove "$DIR" # Refuses dirty worktrees
    git branch -d "agent/${NAME}" # Refuses unmerged branches
    echo "Worktree supprimé : $DIR"
    ;;
  merge)
    echo "Merge through the reviewed PR and required checks." >&2
    exit 1
    ;;
esac
```

Regole di sicurezza del cantiere:

- Un worktree = un agente = un'attività. Mai due agenti nello stesso worktree.
- L'albero di lavoro principale (mano) è riservato agli esseri umani e CI.
- Qualsiasi agente di lavoro deve essere creato da un ramo pulito (no WIP).
- La fusione di un agente operaio è ALWAYS passato attraverso una revisione umana.
- Pulisce i worktrees dopo la fusione: un orfano è il debito.

**Efficace isolamento.** Un worktree condivide le ref e parte della configurazione aggiuntiva Git, così come le credenziali/caches dell'account utente se nulla li separa. ## Sfruttando la recensione Codex in macchina: decodifica automatica

Con la classificazione di gravità della situazione 5] sezione (passo) 7) e [e]ADT `ReviewResult` Sezione: 7B, un output temporaneo Codex** già ordinato e supportato** I risultati grezzi del modello rimangono in una fase di smistamento: solo una prova, una regola deterministica o una decisione umana li promuovono alla porta.

```scala
import io.circe.parser.decode
import zio.*

object CodexReviewGate:

  def parse(raw: String): IO[LlmError, ReviewResult] =
    // Les modèles entourent parfois le JSON de ```json ... ``` malgré la consigne — nettoyage défensif
    val cleaned = raw.replaceAll("(?s)```json|```", "").trim
    ZIO.fromEither(decode[ReviewResult](cleaned))
      .mapError(e => LlmError.Decode(s"Sortie Codex non conforme : ${e.getMessage}"))

  // Le gate ne reçoit que des findings préalablement validés :
  // BLOCKING et REGRESSION_RISK doivent être vides (ou contestés explicitement).
  def gate(review: ReviewResult): IO[String, Unit] =
    val blocking = review.findings.filter(f =>
      f.severity == Severity.Blocking || f.severity == Severity.RegressionRisk
    )
    ZIO
      .fail(
        blocking
          .map(f => s"[${f.severity}] ${f.file} — ${f.message}")
          .mkString("Retours à traiter avant merge :\n", "\n", "")
      )
      .when(blocking.nonEmpty)
      .unit
```

Si noti la simmetria con il principio guida: l'uomo rimane l'arbitro (può sfidare un `BLOCKING`]), ma il percorso predefinito è deterministico. Un output non-parsable Codex fa fallire il cancello — un recensore che non rispetta il formato concordato non convalida nulla.

## GitHub Copilot: strato GitHub-nativo, non terzo profondo recensore aggiunto

Se il restitorio vive su richiesta GitHub, Copilot aggiunge valore aggiunto per arrivare Claude Code e non è così Codex **Il flusso di lavoro GitHub**, non come terzo gatto generalista in ordine IntelliJ. Il mondo del lavoro **GitHub Copilot Approfondimento** aggiunge una vista "Il mio lavoro" per navigare problemi e PR, avviare una sessione da un problema, controllare i controlli, richiedere la correzione di un commento o commento CI e, se lo permettete, pilotare l'atterraggio della PR. Utilizzare questa superficie come un controllo piatto GitHub ; custodia IntelliJ + Claude Code per l'impegnativa implementazione locale e Codex per la recensione indipendente.

```text
Issue GitHub bien spécifiée
→ Copilot coding agent possible pour une petite tâche bornée
→ PR
→ CI déterministe
→ Copilot Code Review automatique
→ Codex Terra / Sol si review profonde nécessaire
→ humain
```

Utilizza dove Copilot è effettivamente utile:

```text
✅ parcourir et prendre en charge des issues depuis GitHub ;
✅ déléguer une petite issue bien bornée à un coding agent ;
✅ créer / suivre une PR et ses checks ;
✅ reviewer automatiquement les nouvelles PR ou les nouveaux pushes ;
✅ proposer des corrections depuis les commentaires de review ;
✅ exploiter AGENTS.md, instructions GitHub, skills et MCP dans la review ;
✅ compléter CodeQL / Code Quality par un signal LLM GitHub-native.
```

Utilizza dove diventa prevalentemente ridondante:

```text
❌ architecture ou bug Scala difficile déjà traité par Opus 5.5 ;
❌ troisième review manuelle systématique après Codex Sol 6.2 ;
❌ deuxième writer sur la même branche pendant qu’un agent principal travaille ;
❌ remplacement de sbt, tests, mutation testing, CodeQL ou review humaine.
```

**Copilot Code Review è un segnale, non un cancello di approvazione.** Una recensione Copilot è pubblicata con l'aggiunta `Comment` stato, non è stato `Approve` o `Request changes`; pertanto non contano come richiesto l'approvazione e non blocca la fusione da sola; è un buon posto per una revisione automatica non friziosa, mentre Codex rimane il recensore indipendente volontariamente attivato su modifiche non banali o rischiose.

La regola della concorrenza rimane la stessa di tutti gli agenti: se l'agente cloud Copilot applica una correzione, Claude Code e Codex non dovrebbe scrivere simultaneamente sulla stessa branca.

### Squadra di flusso di lavoro: adozione graduale, non tre agenti obbligatori

- **Codice recensione**: inizia con : `Standard`, `Quick` per cambiamenti di routine, `Deep` per deposizioni critiche. Anthropic sceglie i modelli; questi livelli non sono gli sforzi di Opus. Configures casual `REVIEW.md` per gli invarianti Scala e la gravità dei risultati; la revisione legge le regole del ramo base o per impostazione predefinita, non quelle proposte dalla PR. Non compila o esegue il codice e il suo controllo non costituisce un veto sulla fusione.
- **PR Stewards**: inizia in modalità manuale ( :`@claude steward`) con un unico repository pilota e un soffitto di spesa. Scrive sul ramo senza chiedere per ogni correzione e anche i processi di boot restituisce. Esclusi dai cambiamenti architettonici della sua delegazione, conflitti semantici, migrazioni e file critici. `@claude stop` o la rimozione dell'etichetta casuale `claude-pr-steward-watching` ferma il monitoraggio delle PR.
- **Claude Approvamenti impegnati**: inizia in direzione `mode: observe` La politica deriva dal ramo predefinito, combina le regole più severe applicabili e può utilizzare i percorsi, realizzati in PR e classificatori. `.claude/approvals.yml`, `REVIEW.md`, `CODEOWNERS`, e flussi di lavoro dovuti CI come file critici. Vedere i limiti di approvazione nella sezione 15A.

Per una PR alternativa Scala, limita lo steward ad una correzione lint, importa, errore di compilazione locale o replicato. Fermare dopo due fallimenti identici, qualsiasi deviazione dal campo o qualsiasi necessità di modificare un invariante. CI un conflitto che colpisce una regola di business non è una correzione meccanica. Queste regole sono il vostro protocollo operativo: devono essere controllati indipendentemente, non assunto dal servizio.

**Claude Ship vs Copilot:** Il servizio Claude può essere rilevante per il volume del team; solo, i comandi locali e le revisioni interconnesse esistenti evitano un nuovo abbonamento e ridistribuzioni. Misurazione su PR comparabili: minuti umani alla fusione, costo totale (reviews, correziones, autorizzazione CI), molto utile trovare, scavare le toppe, il numero di spinte, difetti sfuggiti e ritorsioni. Anthropic sul suo riposo riguarda un processo completo, non un effetto causale isolato di Claude Ship o una specifica prova a voler Scala.

#### Modalità di gol: persistente e verificabile obiettivo

`/goal <objective>` allega l'obiettivo e i suoi criteri per il completamento della sessione. `/goal` mostra l'obiettivo; `/goal edit`, `/goal pause`, `/goal resume`, e l'amore `/goal clear` consentire di modificare, sospendere, riprendere o rimuoverlo. In Desktop, utilizza i controlli di avanzamento. Scala codice, mantenere lo stesso worktree e la prova della spec; non scrivere più in parallelo; il modello deve essere in grado di verificare la visualizzazione CI e i resoconti pubblicati su retromarcia GitHub con gli strumenti realmente disponibili.

Template per una PR esistente, dopo che la spinta è stata autorizzata sul suo ramo (opzioneGPT‑6.2 Sol Medio):

```text
/goal Bring the current pull request to a verified, merge-ready state.

Use the approved spec and AGENTS.md. Confirm the PR URL, base branch, head branch and initial SHA.
Monitor GitHub required CI checks, mergeability and published review feedback. Before each action,
refresh the PR state and verify its head SHA. Stop on unexpected changes or concurrent writers.

Fix only verified branch-related failures and actionable findings within the approved scope.
Resolve conflicts only when the intended behavior is unambiguous. Keep diffs minimal.
Never weaken tests, assertions, security checks or CI requirements. Do not change public contracts,
dependencies, build configuration, workflows or database schemas without explicit approval.
Retry clearly transient failures at most three times; never patch unrelated flaky tests or infrastructure.
After each fix, run the required targeted checks, commit and push only to the authorized PR branch.
Reassess required checks and review feedback on the new SHA; require independent review of the final diff.
Never approve, merge, force-push, or reply to human reviewers or resolve their threads without authorization.

Stop when required checks pass on the latest SHA, no actionable findings or conflicts remain,
and independent review or human approval is the only remaining gate. Stop also if the PR closes,
permissions are missing, the scope must expand, the same root cause fails twice, or 60 minutes elapse.
If checks are still pending or unavailable, report them as such; do not claim the PR is ready.
Finish with a concise report in French containing the PR URL, final SHA, CI status, fixes pushed,
independent review status, unresolved findings and blockers.
```

La lunghezza di attesa 60 Interruzione o pausa l'obiettivo se necessario; non confondere "oggettivi raggiunti" e l'approvazione della merge.

#### Battiti cardiaci: follow-up ricorrente senza continue sessioni di ragionamento

Le attività programmate in un gatto (Heartbeats) riutilizzano il suo contesto e consentono brevi intervalli in minuti. OpenAI documenta il caso di tracciare una PR e di elaborare nuovi ritorni. Preferisci questo meccanismo se il tempo di attesa CI In locale, il post deve rimanere acceso e l'applicazione Desktop attiva. Prima prova un'esecuzione manuale, poi controlla in Schedulated il modello, lo sforzo, la sandbox, le autorizzazioni e le condizioni di spegnimento. Non presumere che il prompt possa disabilitare l'operazione: controllarne lo stato e disabilitarlo manualmente se necessario.

Template da inviare nella chat Codex della PR (senza Goal active mode):

```text
Create a recurring follow-up in this conversation every 10 minutes for the current GitHub pull request.
Use GPT-6.2 Sol Medium if selectable. Keep the same approved spec and AGENTS.md constraints.
Confirm the PR URL, authorized branch, initial SHA, available GitHub tools and schedule before writing.

At each run:
- Refresh the head SHA, required checks, mergeability and published review feedback.
- Deduplicate by repository, PR, SHA and finding/check ID. If nothing actionable changed, return briefly.
- Stop on unexpected branch changes, concurrent writers, unavailable permissions or out-of-scope findings.
- Fix only verified branch-related failures and actionable authorized findings. Run targeted tests,
  commit and push only to the PR branch. Recheck the new SHA.
- Preserve all validation requirements and public contracts. No unrelated refactors, CI or dependency changes.
- Retry transient failures at most three times in total; stop after two failed fixes for the same root cause.
- Never approve, merge, force-push or interact with human review threads without authorization.

Keep a record of the run count, latest SHA, handled findings and retry counts across runs.
Stop and disable the follow-up when required checks pass on the latest SHA, there are no conflicts or
remaining actionable findings, and only independent review or human approval remains; also stop if the PR
closes, human help is needed, six runs have completed, or 60 minutes have elapsed.
If automatic disabling is unavailable, report that the schedule must be disabled manually and perform no more edits.
Report meaningful changes only, in French; include the final PR URL, SHA, checks, fixes and blockers.
```
