# 10. Managing context and costs

## Recommended pipeline

```text
Sourcebot / ScalaSemantic / Codebase-Memory si polyglotte / rg / IntelliJ
→ workers isolés si exploration volumineuse
   ├── recherche / codebase
   ├── graphe sémantique Scala / impact structurel JVM
   ├── Metals / types / diagnostics

   └── documentation
→ résumés courts
→ Claude Code parent : plan + petit diff
```

## To be compressed with RTK / Headroom

* logs CI;
* long `sbt test` exits;
* large `git diff`;
* `rg` massive;
* JSON voluminous;
* long documentation;
* file listings.

<!-- section: s-3 -->
## Not aggressively compressing

* source code to be modified;
* critical tests;
* `build.sbt` ;
* migration;
* stack traces Scala complex;
* Implicit/given errors;
* public JSON contracts.

The five cumulative cost levers are: routing to low-cost models, context compaction, quick scoping with file paths, quick caching and Batch API when it is adapted.

> **Context rot.** Do not confuse three different limits:
>
> ```text
> capacité physique     = combien de tokens entrent dans la fenêtre ;
> récupération          = le modèle retrouve-t-il encore l'information pertinente ;
> raisonnement utile    = sait-il encore l'appliquer correctement parmi tout le reste ?
> ```
>
> Literature 2026 shows that the last two can gradually deteriorate **long before** saturation
> In the same task, adding unnecessary context can reduce quality even when relevant information
> is always present. The typical symptoms of a long session are: old constraints less
> Highlighting, feedback from already refuted assumptions, repeated rereading of the same files, correction loops and abandonment
> premature despite sufficient information.
>
> A long transcript is therefore not a better memory. In a code session, it also accumulates `rg`, outputs
> MCP,
> logs, old versions of the diff, test results, documentation and dead end. **working set decision** must
> Stay small:
>
> ```text
> objectif + contraintes + plan + décisions + diff courant + preuves essentielles
> ```
>
> Compaction (`/compact`) remains a loss compression: it occurs after accumulation and can
> sum up a discrete invariant, a refuted hypothesis or a rare detail. **Do not treat it as a normal mechanism of
> continuation.** For an important task, prefer an explicit and controlled handoff (`HANDOFF.md` or status file),
> then a fresh session. The structural parade remains the ** insulation upstream**: delegate the voluminous exploration,
> independent logs, tests, documentation and investigations to sub-agents with their own context,
> then bring back only short, bleak conclusions.
>
> ```text
> 100K tokens explorés dans un worker
> → 1–2K tokens de résultat
> → parent propre pour décider et écrire
> ```
>
> This rule also applies to the review: **does not give to Codex the full transcript of a long session Claude**.
> Give him a fresh window with `spec + diff final + fichiers modifiés + tests + invariants`. You get both
> model insulation and context insulation.

For the explicit cache OpenAI, reason in total cost : a writing to 1,25× without any re-use costs more than a normal call. With at least one re-use of the same prefix during the life of the cache, one write then read to 0,1× cost 1,35× in total against 2× without cache. Therefore activates a breakpoint only for a stable prefix whose reuse is probable, and measures separately tokens written, tokens read, hit rate and invalidations.

## The four canonical strategies of context engineering

The discipline has been formalized end 2025 sous le nom de **context engineering** — definition Anthropic"all the strategies for curing and maintaining the optimal set of tokens during inference"; Karpathy formulation: "fill the context window with exactly the right information for the next step." The reference taxonomy (LangChain) distinguishes four strategies, which this practical guide already separately — to name them allows to verify that none is forgotten:

| Strategy    | Question asked                                      | Implementation in this guide                                                                                      |
|--------------|-----------------------------------------------------|------------------------------------------------------------------------------------------------------------------|
| **Write**    | What must survive out of the window?    | `AGENTS.md`, `MIGRATION_STATE.md`, auto-memory, task logs, debt register                            |
| **Select**   | What enters the window, and when?     | Sourcebot / ScalaSemantic / Codebase-Memory / rg / Metals MCP, just-in-time recovery                        |
| **Compress** | What can lose tokens without a signal?  | RTK / Headroom on logs and diffs, truncated outputs, structured handoff; `/compact` only as a last resort |
| **Isolate**  | What should live in a separate window? | Subagents read-only, worktrees, reviewer no-write, separate sessions per task                                 |

Two operational rules that arise from this grid and that the rest of the guide does not explicitly cover:

- **Progressive release of tools** : each server MCP add its tool schemas to the window of each session. Limit the servers and tools activated per agent (theACP d'IntelliJ and Claude Code allow) and prefers discovery to demand — the roadmap MCP of August 2026 of the *progressive discovery* of the catalogues of tools a priority of protocol. **Jev can be used as a pre-selector** : choose a few candidate skills/tools before loading their definitions in the context of the LLM.
- **Compaction as a decision, not as a reflex** : a score Jev may report `topic_shift` or `old_context_still_needed`, but it is the harness that then decides to compact. Never let the decision model rewrite the history itself; preserves the decisions and artifacts lasting in `HANDOFF.md` / `MIGRATION_STATE.md`.
- **Selection target**: If a context element does not change any decision of the current step, it does not belong to the window. Periodically measure the share of tokens that have actually influenced the output (hit cache rate, redundancy of injected files): a large window is not an excuse for an unfiltered context.

>
> **Qwen Code now makes this budget observable.** The 0.23 versions show the share of the context consumed by the
> quick system, built-in tools, MCP, memory, skills and messages. Versions 0.24.x add assignment of
> Cost
> in tokens to context/extension files, limits on large *tool surfaces*, a toolallowlist by
> subagent and the construction of the prompt system from the **resident tool set** actually active.
> can stay out of the prefix while preserving the quick cache. Use these metrics as an empirical audit:
> **retrieve or differ a provider, extension or tool that regularly consumes context without changing a
> decision**.

> **Figures and cascades for this budget.** The work 2025-2026
> converging on an objective of use of **~30–40 % of window** in normal operation (a window of 200K aims
> ~60–80K of actual content, not 190K): beyond, the *context rot* even installs with remaining capacity.
> concrete results to be integrated:
> - **design tool outputs first** : silent modes, truncation (e.g. > 2 000 Tokens → written on
>   disk + preview of 10 lines), actionable fields rather than JSON raw. This extends the actual context of
>   ~3–4× without any compression infrastructure; summarize by LLM what a tool might not have emitted is
>   the paid version of the same problem;
> - **observation masking before summary LLM** : a benchmark JetBrains on SWE-bench Verified shows that
>   replace old tool outputs with placeholders (keeping the action/reasoning skeleton)
>   reduces the cost of ~52 % without prolonging trajectories, while the summary LLM pure (−50 % of cost) increase the
>   trajectories of ~15%. Layers without LLM treat the majority of pressure; the summary is the expensive backstop;
> - **structured summary with fixed fields** (intent, progression, key facts, artifacts, next steps, questions
>   open): they beat free prose, but ** no approach preserves the trace of artifacts** (file
>   (d) — hence the state file kept out of the compression pipeline, and vigilance on the
>   "summary summaries" that lose the details of the first hours.
>
> These practices respond to the four failure modes named in the reference taxonomy: *context poisoning*
> (a loop-referenced hallucination), *context distraction* (the model overrides history to the detriment of
> *context confusion* (of superfluous content degrades even without saturation — canonical case: failure with
> 46 tools, success with 19with identical window) and *context clash* (a correction coexists with the error
> which she replaces, ~−39 % performance). These are the root causes that Write / Select / Compress / strategies
> Isolate above neutralize one by one.

> **Industrial validation, not a controlled benchmark.** GitHub documented runtime migration
> Copilot from TypeScript to **832 378 production lines of Rust**, delivered gradually in **128 PRs**. The return
> of experience measured **96,22 % cache reads** on the volume of input tokens and **5 116 compactions** ; the
> Subagents
> spend their context in a separate window and then only return their response to the parent, while the
> sessions
> which write in parallel have their own branch and worktree. This is a very strong industrial confirmation
> of the **stable prefix + Isolate + map→reduce + worktrees**, but not a causal evidence generalizable to all deposits.
>
> The same return stresses two safeguards already present here: the ** E2E tests must remain an independent oracle
that
> the agent cannot rewrite silently**, and migration must **translate behavior first, redesign
> **. For migration Scala/JVM, therefore, protects characterization tests and contracts before giving to
> Writer
> permission to modify the implementation.

#### Decision tree: continue vs handoff + cool session vs `/compact`

The most costly error in credits is to continue a polluted session. Here is the decision tree to apply all ~15 interactions or as soon as a symptom of context rot appears:

```text
Session en cours
│
├─ L'agent répète une hypothèse déjà réfutée ou accumule les erreurs ?
│  └─ OUI → STOP → HANDOFF.md vérifié → nouvelle session
│             (ne PAS changer seulement de modèle dans la conversation polluée)
│
├─ Le contexte contient > 50 % de tokens non décisionnels
│  (logs bruts, rg massif, anciennes versions du diff) ?
│  └─ OUI → écrire HANDOFF.md :
│             objectif, contraintes, plan, décisions, artefacts,
│             diff courant, preuves, erreurs non résolues, prochaine action
│           → relire le handoff
│           → nouvelle session avec ce working set minimal
│
├─ La tâche a changé de nature ?
│  (bugfix → refactor, feature → migration)
│  └─ OUI → nouveau cadrage complet (Étape 0) + nouvelle session
│
├─ Le modèle utilise encore correctement les invariants et non-objectifs ?
│  └─ NON → ré-injecter la charte si le contexte reste sain ;
│           sinon handoff + nouvelle session
│
└─ Aucune condition ci-dessus → continuer
```

`/compact` becomes the **plan B**, reserved for cases where the surface requires to keep the session. Before using it, have a structured handoff produced and then reread; after compaction, explicitly checks that the invariants, decisions, artifacts and open errors have survived. If critical detail is missing, abandon the compacted session.

Metric rule: if ratio (tokens in window) / (tokens actually cited or used in the 3 last replies) exceeded 5:1, the session is overweight. The defect is **handoff + fresh session**, no more compression.

## Example: Structure a cached request in Scala 3

The discipline of the section 4 (static at the top, dynamic at the bottom) translates directly into the building of the query. `cache_control` are invoiced ~5 à 10 % of input rate from second call (5 % on Sonnet 5.5 and Opus 5.5) — provided that the byte for byte is identical between calls:

```scala
import io.circe.Json
import io.circe.syntax.*

object CacheablePrompt:

  // STATIQUE — chargé une fois au démarrage, jamais reconstruit dynamiquement :
  // toute interpolation (timestamp, compteur...) dans ces blocs casse le cache.
  def systemBlocks(agentsMd: String, scalaRules: String): Json =
    Json.arr(
      Json.obj(
        "type"          -> "text".asJson,
        "text"          -> agentsMd.asJson,
        "cache_control" -> Json.obj("type" -> "ephemeral".asJson)
      ),
      Json.obj(
        "type"          -> "text".asJson,
        "text"          -> scalaRules.asJson,
        "cache_control" -> Json.obj("type" -> "ephemeral".asJson)
      )
    )

  // DYNAMIQUE — change à chaque itération, va dans messages, jamais dans les blocs cachés
  def userMessage(diff: String, compileErrors: String): Json =
    Json.obj(
      "role"    -> "user".asJson,
      "content" -> s"Diff courant :\n$diff\n\nErreurs :\n$compileErrors".asJson
    )

  def request(agentsMd: String, scalaRules: String, diff: String, errors: String): Json =
    Json.obj(
      "model"      -> "claude-sonnet-5-5".asJson,
      "max_tokens" -> 4096.asJson,
      "system"     -> systemBlocks(agentsMd, scalaRules),
      "messages"   -> Json.arr(userMessage(diff, errors))
    )
```

Check the hit cache in the answer (`usage.cache_read_input_tokens > 0`) and log it: a crashing bit cache rate almost always signals a fast header that has become unstable — exactly the bug of the 4 rule in the section
