# Script utility: scripts/ai-worktree.sh

```sh
#!/usr/bin/env bash
# Usage: ./scripts/ai-worktree.sh create|list|remove|merge <name> [base]
set -euo pipefail
ACTION="${1:-list}"
NAME="${2:-}"
BASE="${3:-main}"
if [[ "$ACTION" != "list" && ! "$NAME" =~ ^[a-zA-Z0-9][a-zA-Z0-9._-]*$ ]]; then
  echo "Invalid worktree name" >&2
  exit 1
fi

case "$ACTION" in
  create)
    BRANCH="agent/${NAME}"
    DIR="../$(basename "$(pwd)")-${NAME}"
    git worktree add "$DIR" -b "$BRANCH" "$BASE"
    echo "Worktree créé : $DIR (branche $BRANCH)"
    echo "cd $DIR && claude"
    ;;
  list)
    git worktree list
    ;;
  remove)
    DIR="../$(basename "$(pwd)")-${NAME}"
    git worktree remove "$DIR" # Refuses dirty worktrees
    git branch -d "agent/${NAME}" # Refuses unmerged branches
    echo "Worktree supprimé : $DIR"
    ;;
  merge)
    echo "Merge through the reviewed PR and required checks." >&2
    exit 1
    ;;
esac
```

Worktree safety rules:

- One worktree = one agent = one task. Never two agents in the same worktree.
- The main worktree (hand) is reserved for humans and CI.
- Any worktree agent must be created from a clean branch (no WIP).
- The merge of a worker agent is ALWAYS passed through a human review.
- Cleans worktrees after merge: an orphan worktree is debt.

**Effective isolation.** A worktree shares the refs and part of the configuration Git, as well as the credentials/caches of the user account if nothing separates them. Give each agent a sandbox with explicit writing roots, a temporary directory, tools MCP in lesser privilege and separate secrets; for unreliable code, prefers a container/VM without mounting `$HOME`, without socket Docker] or production keys. In local, refuses the full-access / bypass; sideCodex configure sandbox and approvals, side Claude sandbox and permissions allow/deny, then tests attempts to write off perimeter and network access prohibited. Hooks are complementary signals/controls, not a boundary of containment.

| Role | Actual rights |
|------|------------------|
| Researcher / Reviewer | Play repository; no push; scratch isolated if reproduction test |
| Writer | Writing in its sandbox and task branch; push only allowed |
| Steward | Corrections on explicitly transferred PR; never merge / force-push |
| CI unreliable | Checkout, compile, tests ; token reading, no privileged secrets |
| Release pipeline | Identity and secrets dedicated to the environment, after human/political gate |

Separates network and token accesses GitHub by role; does not give deployment credentials to the agent. PR comments, logs and unreliable files are data, no new permissions.

## Exploiting the review Codex in machine: typed decoding

With the severity classification of the 5] section (step 7) and [ADT `ReviewResult` section 7B, an output Codex** already sorted and supported** becomes a data usable by a merge gate rather than a text to be read again. The raw findings of the model remain in a sorting step: only a test, deterministic rule or a human decision promote them to the gate.

```scala
import io.circe.parser.decode
import zio.*

object CodexReviewGate:

  def parse(raw: String): IO[LlmError, ReviewResult] =
    // Les modèles entourent parfois le JSON de ```json ... ``` malgré la consigne — nettoyage défensif
    val cleaned = raw.replaceAll("(?s)```json|```", "").trim
    ZIO.fromEither(decode[ReviewResult](cleaned))
      .mapError(e => LlmError.Decode(s"Sortie Codex non conforme : ${e.getMessage}"))

  // Le gate ne reçoit que des findings préalablement validés :
  // BLOCKING et REGRESSION_RISK doivent être vides (ou contestés explicitement).
  def gate(review: ReviewResult): IO[String, Unit] =
    val blocking = review.findings.filter(f =>
      f.severity == Severity.Blocking || f.severity == Severity.RegressionRisk
    )
    ZIO
      .fail(
        blocking
          .map(f => s"[${f.severity}] ${f.file} — ${f.message}")
          .mkString("Retours à traiter avant merge :\n", "\n", "")
      )
      .when(blocking.nonEmpty)
      .unit
```

Note the symmetry with the guiding principle: the human remains the referee (he can challenge a `BLOCKING`]), but the default path is deterministic. A non-parsable Codex output makes the gate fail — a reviewer that does not respect the agreed format does not validate anything.

### Workflow team: gradual adoption, not three mandatory agents

- **Code Review**: starts with `Standard`, `Quick` for routine changes, `Deep` for critical depositions. Anthropic chooses the models; these levels are not Opus's efforts. Configures `REVIEW.md` for the invariants Scala and the severity of the findings; the review reads the rules of the base branch or by default, not those proposed by the PR. It does not compile or execute the code and its check does not constitute a veto on the merge.
- **PR Steward**: starts in manual mode (`@claude steward`) with a single pilot repository and a spending ceiling. He writes on the branch without asking for each correction and also processes boot returns. Excludes from his delegation architectural changes, semantic conflicts, migrations and critical files. `@claude stop` or the removal of the label `claude-pr-steward-watching` stops the monitoring of the PR.
- **Claude Approvals**: starts in `mode: observe` without making the check blocking. The policy comes from the default branch, combines the strictest applicable rules and can use paths, made of PR and classifiers. Protects `.claude/approvals.yml`, `REVIEW.md`, `CODEOWNERS`, and workflows CI as critical files. See the approval limits in section 15A.

For a PR Scala, limits the steward to a lint correction, import, local compilation error or replicated finding. Stop after two identical failures, any deviation from the scope or any need to modify an invariant. Never ask him to make the CI green by weakening a test, assertion or check. A conflict that affects a business rule is not a mechanical correction. These rules are your operating protocol: they must be controlled independently, not assumed by the service.

**Claude Ship vs Copilot :** These are partially competing post-PR layers. Keeps a single default automatic review stream and a single proofreader per branch. Claude service can be relevant for team volume; solo, local commands and existing cross-view avoid a new subscription and redundant reviews. Measurement on comparable PRs: human minutes to the merge, total cost (reviews, corrections, CI), really useful finding, overscope patches, number of pushes, escaped defects and reverts. The volume gains and reverts announced by Anthropic on his own rest concerns a complete process, not an isolated causal effect of Claude Ship or a specific evidence to Scala.

#### Goal mode: persistent and verifiable goal

`/goal <objective>` attaches the objective and its criteria for completion to the session. In the CLI, `/goal` displays the objective; `/goal edit`, `/goal pause`, `/goal resume`, and `/goal clear` allow to modify, suspend, resume or remove it. In Desktop, uses the progress controls. For local Scala code, keep the same worktree and the evidence of the spec; no further writing in parallel. The model must be able to verify the CI and the published returns on GitHub with the tools actually available.

Template for an existing PR, after the push has been authorized on its branch (GPT‑6.2 Sol Medium):

```text
/goal Bring the current pull request to a verified, merge-ready state.

Use the approved spec and AGENTS.md. Confirm the PR URL, base branch, head branch and initial SHA.
Monitor GitHub required CI checks, mergeability and published review feedback. Before each action,
refresh the PR state and verify its head SHA. Stop on unexpected changes or concurrent writers.

Fix only verified branch-related failures and actionable findings within the approved scope.
Resolve conflicts only when the intended behavior is unambiguous. Keep diffs minimal.
Never weaken tests, assertions, security checks or CI requirements. Do not change public contracts,
dependencies, build configuration, workflows or database schemas without explicit approval.
Retry clearly transient failures at most three times; never patch unrelated flaky tests or infrastructure.
After each fix, run the required targeted checks, commit and push only to the authorized PR branch.
Reassess required checks and review feedback on the new SHA; require independent review of the final diff.
Never approve, merge, force-push, or reply to human reviewers or resolve their threads without authorization.

Stop when required checks pass on the latest SHA, no actionable findings or conflicts remain,
and independent review or human approval is the only remaining gate. Stop also if the PR closes,
permissions are missing, the scope must expand, the same root cause fails twice, or 60 minutes elapse.
If checks are still pending or unavailable, report them as such; do not claim the PR is ready.
Finish with a concise report in French containing the PR URL, final SHA, CI status, fixes pushed,
independent review status, unresolved findings and blockers.
```

The length of 60 minutes and meters are proposed mission limits, not timeouts guaranteed by the product. Interrupt or pause the goal if necessary; do not confuse "objective achieved" and approval of the merge.
