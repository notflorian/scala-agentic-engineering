# Dienstprogramm-Skript: scripts/ai-worktree.sh

```sh
#!/usr/bin/env bash
# Usage: ./scripts/ai-worktree.sh create|list|remove|merge <name> [base]
set -euo pipefail
ACTION="${1:-list}"
NAME="${2:-}"
BASE="${3:-main}"
if [[ "$ACTION" != "list" && ! "$NAME" =~ ^[a-zA-Z0-9][a-zA-Z0-9._-]*$ ]]; then
  echo "Invalid worktree name" >&2
  exit 1
fi

case "$ACTION" in
  create)
    BRANCH="agent/${NAME}"
    DIR="../$(basename "$(pwd)")-${NAME}"
    git worktree add "$DIR" -b "$BRANCH" "$BASE"
    echo "Worktree créé : $DIR (branche $BRANCH)"
    echo "cd $DIR && claude"
    ;;
  list)
    git worktree list
    ;;
  remove)
    DIR="../$(basename "$(pwd)")-${NAME}"
    git worktree remove "$DIR" # Refuses dirty worktrees
    git branch -d "agent/${NAME}" # Refuses unmerged branches
    echo "Worktree supprimé : $DIR"
    ;;
  merge)
    echo "Merge through the reviewed PR and required checks." >&2
    exit 1
    ;;
esac
```

Regeln für die Sicherheit der Arbeit :

- Ein Worktree = ein Agent = eine Aufgabe. Nie zwei Agenten im selben Worktree.
- Das Hauptworktree (Hand) ist für den Menschen und die CI reserviert.
- Jeder worktree agent muss aus einem eigenen Zweig erstellt werden (keine WIP).
- Der Merge eines Worktree Agents geht immer durch eine menschliche Bewertung.
- Reinigt Worktrees nach merge: ein Waise Worktree ist Schulden.

**Die Isolierung ist wirksam.** Ein Worktree teilt refs und einen Teil der Konfiguration Git, sowie die Credentials/Caches des Benutzerkontos, wenn sie nicht getrennt werden. Gibt jedem Agenten eine Sandbox mit expliziten Schreibwurzeln, ein temporäres Verzeichnis, Werkzeuge MCP weniger Privilegien und separate Geheimnisse; für unzuverlässigen Code, bevorzugt einen Container/VM ohne Montage von `$HOME`, ohne Socket Docker oder Produktionsschlüssel. Auf lokaler Ebene, lehnt die full-access / bypass ; Seite Codex konfiguriert Sandbox und Genehmigungen, Seite Claude Sandbox und allow/deny Berechtigungen, und testet dann Versuche, außerhalb der Umgebung zu schreiben und Netzwerkzugriff verboten. Hooks sind ergänzende Signale/Kontrollen, keine Sperrgrenze.

| Rolle | Tatsächliche Ansprüche |
|------|------------------|
| Researcher / reviewer | Repository-Lese ; kein Push ; Scratch isoliert, wenn Reproduktionstest |
| Writer | Schreiben in seine Sandbox und Task-Zweig; Push nur erlaubt |
| Steward | Korrekturen auf der ausdrücklich übertragenen PR; nie merge / force-push |
| CI unzuverlässig | Checkout, kompilieren, testen; token lesen, keine bevorzugten Geheimnisse |
| Release Pipeline | Identität und umweltspezifische Geheimnisse, nach menschlichem/politischem Gate |

Trennt Netzwerkzugriff und tokens GitHub nach Rolle ; gibt dem Agenten keine Freigabe-Credentials. Kommentare von PR, Logs und unzuverlässigen Dateien sind Daten, keine neuen Berechtigungen.

## Review Codex als Maschine ausnutzen: Typische Dekodierung

Mit der strengen Klassifizierung des Abschnitts [5 (Schritt 7] und ADT `ReviewResult` im Abschnitt [7B wird eine Ausgabe [Codex ** bereits sortiert und gestützt** zu einer Datenquelle, die von einem Merge-Gate anstelle eines zu wiederholenden Textes genutzt werden kann. Die Rohwerte des Modells bleiben in einem Sortierschritt: Nur ein Test, eine Bestimmungsregel oder eine menschliche Entscheidung fördern das Gate.

```scala
import io.circe.parser.decode
import zio.*

object CodexReviewGate:

  def parse(raw: String): IO[LlmError, ReviewResult] =
    // Les modèles entourent parfois le JSON de ```json ... ``` malgré la consigne — nettoyage défensif
    val cleaned = raw.replaceAll("(?s)```json|```", "").trim
    ZIO.fromEither(decode[ReviewResult](cleaned))
      .mapError(e => LlmError.Decode(s"Sortie Codex non conforme : ${e.getMessage}"))

  // Le gate ne reçoit que des findings préalablement validés :
  // BLOCKING et REGRESSION_RISK doivent être vides (ou contestés explicitement).
  def gate(review: ReviewResult): IO[String, Unit] =
    val blocking = review.findings.filter(f =>
      f.severity == Severity.Blocking || f.severity == Severity.RegressionRisk
    )
    ZIO
      .fail(
        blocking
          .map(f => s"[${f.severity}] ${f.file} — ${f.message}")
          .mkString("Retours à traiter avant merge :\n", "\n", "")
      )
      .when(blocking.nonEmpty)
      .unit
```

Beachten Sie die Symmetrie mit dem Leitprinzip: Der Mensch bleibt der Schiedsrichter (er kann eine `BLOCKING` anfechten), aber der Standardpfad ist deterministisch. Ein nicht parsable Ausgang Codex lässt den Gate fehlschlagen ✓ ein Reviewer, der das vereinbarte Format nicht respektiert, nichts gültig.

## GitHub Copilot : Schicht GitHub-native, nicht dritte tiefe Überprüfung

Wenn der repository lebt auf GitHub, Copilot bringt einen zusätzlichen Wert zu Claude Code und Codex **auf Workflow-Ebene GitHub**, nicht als dritte allgemeine Katze in IntelliJ. La **GitHub Copilot app** fügt eine Ansicht hinzu, um durch die Ausgabe und PR zu gehen, eine Sitzung von einer Ausgabe aus zu starten, Checks zu überprüfen, die Korrektur eines Kommentars oder eines Kommentars zu verlangen CI rot und, wenn du es zulässt, die Landung der PR steuern. Verwende diese Oberfläche als ebene Kontrolle GitHub ; Wache IntelliJ + Claude Code für die anspruchsvolle lokale Implementierung und Codex für die unabhängige Bewertung.

```text
Klar spezifiziertes GitHub-Issue
→ Copilot Coding Agent als Option für eine kleine abgegrenzte Aufgabe
→ PR
→ deterministische CI
→ automatisches Copilot Code Review
→ Codex Terra / Sol, wenn ein gründliches Review nötig ist
→ Mensch
```

Anwendungen, bei denen Copilot wirklich nützlich ist:

```text
✅ Issues direkt in GitHub durchsuchen und übernehmen;
✅ ein kleines, klar abgegrenztes Issue an einen Coding Agent delegieren;
✅ einen PR erstellen oder begleiten und seine Checks verfolgen;
✅ neue PRs oder Pushes automatisch überprüfen;
✅ Korrekturen aus Review-Kommentaren vorschlagen;
✅ AGENTS.md, GitHub-Anweisungen, Skills und MCP beim Review nutzen;
✅ CodeQL / Code Quality durch ein GitHub-natives LLM-Signal ergänzen.
```

Anwendungen, bei denen es vor allem redundant wird:

```text
❌ Architektur oder schwierige Scala-Fehler, die Opus 5.5 bereits bearbeitet;
❌ routinemäßiges drittes manuelles Review nach Codex Sol 6.2;
❌ zweiter implementierender Agent auf demselben Branch, während der Hauptagent noch arbeitet;
❌ Ersatz für sbt, Tests, Mutation Testing, CodeQL oder menschliches Review.
```

**Copilot Code Review ist ein Signal, kein Gate-Akkreditierung.** Copilot-Review wird mit Status veröffentlicht `Comment`nicht `Approve` oder `Request changes` ; es zählt also nicht als erforderliche Genehmigung und blockiert nicht das Merge allein. Es ist ein guter Platz für eine automatische, wenig rigid, während Codex bleibt der unabhängige Reviewer, der freiwillig auf nicht triviale oder riskante Änderungen ausgelöst wird.

Die Wettbewerbsregeln bleiben die gleiche wie für alle Agenten: Wenn Copilot Cloud Agent einen Patch anwendet, Claude Code und [Codex] müssen nicht gleichzeitig auf denselben Zweig schreiben. Benutzt eine klare Delegation oder einen separaten Zweig oder einen Worktree, und lässt den Diff vom Menschen entscheiden.

**Claude Ship** ist eine Schicht GitHub Nach der Implementierung, unabhängig vom Coding Agent, der die PR produziert hat. Sie trennt drei Verantwortlichkeiten: Fehler zu finden, Korrekturen vorzunehmen und eine Genehmigungspolitik zu bewerten. `/code-review` oder Ultrareview (Reviews auf Anfrage).

### Workflow solo: `/ship` oder `/steward` mit Codex und Claude Code

```text
Codex oder Claude implementiert → Spezifikation erfüllt + lokale Tests grün
→ Diff, unversionierte Dateien und Secrets vor jedem Push prüfen
→ PR öffnen; /ship, wenn du zusätzlich ein lokales Claude-Review möchtest
```

Für deinen Gebrauch Claude Max + Codex testet zuerst `/steward` auf einem kleinen PR: Vermeidet es, eine ursprüngliche Review zu revidieren, wenn Opus/Sol dies bereits getan hat. Wenn Claude den Code geschrieben oder korrigiert hat, behält Codex als unabhängiges review. Wenn Codex schrieb und Claude auch die Korrekturen angewendet hat, verlangt er eine kühle review der Korrekturen durch Codex und relinkt das gesamte diff ; zwei Vorlagen bilden nicht automatisch zwei unabhängige Urteile.

**Achtung! `/ship` :** der Befehl kann unkomprimierte Änderungen, einschließlich nicht verfolgter Dateien, eintragen und ohne interaktive Bestätigung blockieren. Zählt nicht auf die Erkennung von sensiblen Dateinamen, um den Inhalt zu schützen. `git status`, das diff staged und unstaged, die neuen Dateien, den Scan von Geheimnissen und remote es vor dem Aufruf. Bevorzugt einen bestimmten Zweig und einen Worktree, dessen Inhalt bereits validiert ist.

Lokale Überwachung kann den wiederhergestellten Code aus GitHub mit deinen Rechten ausführen: aktiviert ihn nur auf einem Projektarchiv und einem Zweig, dessen autorisierte Beitragszahler vertrauenswürdig sind. Lassen Sie keinen Kommentar von PR-Verbreiterung des Spektons oder der Berechtigungen. Verwenden Sie eine Umgebung ohne Produktionsgeheimnisse und stoppen Sie die Schleife mit [`/ship stop` (oder Unterbrechung der Sitzung), bevor Sie auf den gleichen Zweig eingreifen. Die nativen Einschränkungen von Aktionen ohne Benutzernachricht ersetzen weder die Regeln GitHub noch lokale Schutzeinrichtungen.

### Workflow-Team: progressive Adoption, nicht drei obligatorische Agenten

- **Review-Code** : beginnt mit `Standard`, `Quick` für Routinewechsel, `Deep` für kritische Einlagen. Anthropic Auswahl der Vorlagen; diese Ebenen sind nicht die Bemühungen von Opus. Konfiguriert `REVIEW.md` für Invarianten Scala und die Schwere der Findings; die Review liest die Regeln des Basis- oder Standard-Zweigs, nicht die von der PR vorgeschlagenen. Sie kompiliert oder führt den Code nicht aus, und ihr Check ist kein Veto gegen das Mege.
- **PR Steward[**: beginnt im manuellen Modus (`@claude steward`) mit einem einzigen Pilot- und Ausgabenobergrenzen. Er schreibt auf den Zweig, ohne für jede Korrektur nachzufragen, und verarbeitet auch die Bots-Rückgaben. Ausschließen von Architekturänderungen, semantischen Konflikten, Migrationen und kritischen Dateien. `@claude stop` oder das Entfernen des Labels `claude-pr-steward-watching` stoppt die Überwachung der PR.
- **Claude Approvals**: beginnt mit `mode: observe`, ohne dass der Check-Blocker blockiert wird. Die Politik kommt aus dem Standardzweig, kombiniert die strengsten anwendbaren Regeln und kann Pfade, Fakten aus PR und Klassifizierungen verwenden. Schutz `.claude/approvals.yml`, `REVIEW.md`, `CODEOWNERS` und Workflows CI als kritische Dateien. Siehe Genehmigungsgrenzen in Abschnitt 15]A.

Für einen PR Scala beschränkt der Steward den Stift auf eine Korrektur von Lint, Import, lokalem Kompilationsfehler oder reproduziertem Finding. Stopp nach zwei identischen Fehlern, jeder Scope-Abstand oder jede Notwendigkeit, einen Invariant zu ändern. Bitte ihn niemals, die [CI] durch Schwächung eines Tests, einer Behauptung oder eines Checks grün zu machen. Ein Konflikt, der eine Berufsregel berührt, ist keine mechanische Korrektur. Diese Regeln sind dein Betriebsprotokoll: Sie müssen unabhängig, nicht durch den Service garantiert, kontrolliert werden.

**Claude Ship vs. Copilot:** Dies sind teilweise konkurrierende Post-PR-Layer. Bewahrt einen einzigen automatischen Standard-Review-Stream und einen einzigen Writer-Patch pro Zweig. Claude-Service kann für das Teamvolumen relevant sein; Solo, die lokalen Befehle und die bestehende Kreuz-Layer vermeiden ein neues Abonnement und redundante Bewertungen. Messung an vergleichbaren PR: Humanminuten bis zum merge, Gesamtkosten (Reviews, Korrekturen, CI), wirklich nützliche findings, off-scope-patchs, Anzahl der Pushes, ausgelaufene Fehler und reverts. Anthropic Claude Ship in seiner eigenen Ruhe einen vollständigen Prozeß, nicht eine isolierte Ursache von Claude Ship oder einen spezifischen Beweis für Scala.

## Positioniernote: A2A gegenüber MCP

Protokoll **A2A (Agent-to-Agent)**, von Google initiiert und dann der Linux Foundation anvertraut, standardisiert Kommunikation *zwischen Bediensteten* von verschiedenen Anbietern (Fähigkeitenentdeckung, Übertragung von Aufgaben, Überwachung der Ausführung), wo MCP standardisiert die Kommunikation *Agent ↔ Werkzeuge*. Für den Workflow dieses Leitfadens, das Urteil Juni 2026 ist einfach: **A2A bringt nichts zu einem solo Dev**. Die Orchestration Claude ↔ Codex Hier wird durch den Menschen beschrieben (und es ist ein Feature: Sie filtern die Rücksendungen), und Subagenten Claude Code haben ihren eigenen nativen Mechanismus.2A wird relevant, wenn eine Industrieorganisation heterogene Agenten (ein Agent Claude, der offiziell einem Vertreter Codex In diesem Fall wird die Laufzeit des Protokolls und seiner Umsetzungen zu diesem Zeitpunkt, nicht vorher, überprüft.
