> Modellisolierung und Kontextisolierung.

Aktiviert daher nur einen Breakpoint für ein stabiles Präfix, dessen Wiederverwendung wahrscheinlich ist, und misst separat geschriebene tokens, tokens lus, Hitrate und Abvalidierungen.

## Die vier kanonischen Strategien des context engineering

Disziplin wurde formalisiert Ende 2025 unter dem Namen **context engineering** Definition Anthropic: Alle Strategien, um die optimale Token-Sammlung während der Inferenz zu curren und zu halten; Karpathy-Formulierung: ✓ das Kontextfenster mit genau den richtigen Informationen für den nächsten Schritt füllen ✓. Die Referenztaxonomie (LangChain) unterscheidet vier Strategien, die dieser Leitfaden bereits separat verwendet wird, um zu überprüfen, dass keines vergessen wird:

| Strategie    | Frage gestellt                                      | Umsetzung in diesem Leitfaden                                                                                      |
|--------------|-----------------------------------------------------|------------------------------------------------------------------------------------------------------------------|
| **Write**    | Was muss aus dem Fenster überleben?    | `AGENTS.md`, `MIGRATION_STATE.md`, auto-memory, Task-Protokolle, Schuldenregister                            |
| **Select**   | Was kommt ins Fenster und wann?     | Sourcebot / ScalaSemantic / Codebase-Memory / rg / Metals MCP, gerade rechtzeitige Erholung                        |
| **Compress** | Was kann Token ohne Signal verlieren?  | RTK /Headroom auf Logs und Diffs, gekürzte Ausgänge, strukturierte Handoff; `/compact` nur als letztes Mittel |
| **Isolat**  | Was muss in einem separaten Fenster leben? | Subagents read-only, worktrees, review no-write, separate Sitzungen pro Auftrag                                 |

Zwei operative Regeln , die sich aus diesem Raster ergeben und die der Rest des Leitfadens nicht ausdrücklich umfasst:

- **Progressive Disclosierung von Werkzeugen** : jeder Server MCP Fügt seine Werkzeugvorlagen in das Fenster jeder Sitzung ein. Begrenzt die Server und Werkzeuge, die pro Agent aktiviert werden (dieACP d'IntelliJ und Claude Code und bevorzugt die Entdeckung nach der Nachfrage, ✓ die Roadmap MCP August 2026 , die die *Progressive Discovery* Werkzeugkataloge eine Priorität des Protokolls. Auf einem großen Katalog **Jev kann als Vorwähler dienen** : Auswahl einiger Skills/Tools, bevor sie ihre Definitionen im Kontext der LLM.
- **Kompakt als Entscheidung, nicht als Reflex** : eine Punktzahl Jev kann berichten `topic_shift` oder `old_context_still_needed`, aber es ist der Harness, der dann entscheidet, zu komprimieren. Lass nie die model decision neu schreiben sich die historische ; bewahrt die nachhaltigen Entscheidungen und Artefakte in `HANDOFF.md` / `MIGRATION_STATE.md`.
- **Auswahlprogramm[** : Wenn ein Kontextelement keine Entscheidung im aktuellen Schritt ändert, gehört es nicht zum Fenster. Maßt in regelmäßigen Abständen den Anteil der Token, die die Ausgabe tatsächlich beeinflusst haben (Hit-Cache, Redundanz der eingespritzten Dateien): Ein großes Fenster ist keine Entschuldigung für einen ungefilterten Kontext.

#### Entscheidungsbaum: weiterhin vs. handoff + frische Sitzung vs. `/compact`

Der teuerste Fehler bei Credits ist, eine verschmutzte Sitzung fortzusetzen. Hier ist der Entscheidungsbaum, um alle ~15 Interaktionen anzuwenden oder sobald ein Symptom von rot context erscheint:

```text
Laufende Sitzung
│
├─ Wiederholt der Agent eine bereits widerlegte Hypothese oder häufen sich Fehler?
│  └─ JA → STOPP → überprüftes HANDOFF.md → neue Sitzung
│             (nicht nur das Modell in derselben überladenen Unterhaltung wechseln)
│
├─ Enthält der Kontext > 50 % für Entscheidungen irrelevante Tokens
│  (Rohlogs, umfangreiche rg-Ausgaben, alte Diff-Versionen)?
│  └─ JA → HANDOFF.md schreiben:
│             Ziel, Vorgaben, Plan, Entscheidungen, Artefakte,
│             aktueller Diff, Belege, ungelöste Fehler, nächste Aktion
│           → Übergabe prüfen
│           → neue Sitzung mit dieser minimalen Arbeitsgrundlage
│
├─ Hat sich die Art der Aufgabe geändert?
│  (Bugfix → Refactoring, Feature → Migration)
│  └─ JA → vollständige neue Aufgabenklärung (Schritt 0) + neue Sitzung
│
├─ Wendet das Modell die Invarianten und Nicht-Ziele noch korrekt an?
│  └─ NEIN → Richtlinien erneut in den Kontext geben, wenn dieser noch brauchbar ist;
│           andernfalls Übergabe + neue Sitzung
│
└─ Keine der obigen Bedingungen erfüllt → weiterarbeiten
```

`/compact` wird der [**plan B**, der nur für Fälle gilt, in denen die Oberfläche die Sitzung beibehalten muss. Vor der Verwendung muss ein strukturiertes Handoff erzeugt und relinkt werden; nach der Komplottierung muss ausdrücklich geprüft werden, ob Invarianten, Entscheidungen, Artefakte und offene Fehler überlebt haben. Wenn ein kritisches Detail fehlt, wird die kompakte Sitzung abgebrochen.

metrische Regel: Wenn das Verhältnis (tokens im Fenster) / (tokens tatsächlich zitiert oder verwendet in den 3 (letzte Antworten) mehr als 5:1, die Sitzung ist übergewichtig. Der Fehler ist **handoff + kühle Sitzung**, nicht mehr Kompression.

## Beispiel: Strukturieren Sie eine versteckte Abfrage in Scala 3

Die Disziplin der Fachgruppe 4 (statisch oben, dynamisch unten) wird direkt in den Aufbau der Abfrage. `cache_control` werden berechnet ~5 à 10 % des Inputtarifs ab dem zweiten Anruf (5 % auf Sonnet 5.5 und Opus 5.5) unter der Voraussetzung , dass Byte für Byte identisch zwischen Anrufen:

```scala
import io.circe.Json
import io.circe.syntax.*

object CacheablePrompt:

  // STATIQUE — chargé une fois au démarrage, jamais reconstruit dynamiquement :
  // toute interpolation (timestamp, compteur...) dans ces blocs casse le cache.
  def systemBlocks(agentsMd: String, scalaRules: String): Json =
    Json.arr(
      Json.obj(
        "type"          -> "text".asJson,
        "text"          -> agentsMd.asJson,
        "cache_control" -> Json.obj("type" -> "ephemeral".asJson)
      ),
      Json.obj(
        "type"          -> "text".asJson,
        "text"          -> scalaRules.asJson,
        "cache_control" -> Json.obj("type" -> "ephemeral".asJson)
      )
    )

  // DYNAMIQUE — change à chaque itération, va dans messages, jamais dans les blocs cachés
  def userMessage(diff: String, compileErrors: String): Json =
    Json.obj(
      "role"    -> "user".asJson,
      "content" -> s"Diff courant :\n$diff\n\nErreurs :\n$compileErrors".asJson
    )

  def request(agentsMd: String, scalaRules: String, diff: String, errors: String): Json =
    Json.obj(
      "model"      -> "claude-sonnet-5-5".asJson,
      "max_tokens" -> 4096.asJson,
      "system"     -> systemBlocks(agentsMd, scalaRules),
      "messages"   -> Json.arr(userMessage(diff, errors))
    )
```

Überprüfen Sie den Hit-Cache in der Antwort ([`usage.cache_read_input_tokens > 0`) und loggen Sie ihn: Ein Hit-Cache-Rate, der zusammenbricht, signalisiert fast immer einen unstabil gewordenen Tempo-Header ✓ genau den Bug der Regel [4] im Abschnitt
