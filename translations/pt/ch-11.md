# 11. Quando usar o Aider e onde entram OpenCode e Qwen Code

Aider continua a ser útil, mantido e muito eficaz para **par programming terminal orientado Git** : são fornecidos arquivos precisos, produz adesivos legíveis, e o histórico Git continua a ser o undo stack.

OpenCode é um agente de código aberto mais generalista, com terminal, IDE/desktop segundo configuração, múltiplas sessões e integrações LSP/MCPPara Scala, isto é interessante, mas há que ser preciso: algumas capacidades LSP estão ainda documentadas como experimentais ou dependentes de um flag de configuração, e **Metals não faz parte dos LSP acid nativemente** - o pedido de integração aberto na apresentação OpenCode (emero) 2026) ainda se encontra em fase de debate em meados de julho 2026Na prática, o feedback compilador Scala confiável em OpenCode passa por um config LSP manual ou pelo **Metals MCP standalone** (secção) 9), que continua a ser a via recomendada. Por conseguinte, não baseie uma decisão de arquitetura de equipamento apenas noOpenCode Pruebe no seu japão, com Metalsy depois mede a qualidade dos diffs.

Qwen Code é agora mais do que um simples arness para Qwen : **Auto-Memory, Auto-Skills, suboficiales, MCPLSP, worktrees Git, modo headless e fornecedores OpenAI/Anthropic/Qwen/ local** Isto converte-o numa alternativa de código aberto séria a Claude Code y CodexAs versões **0.24.x** Eles reforçam precisamente os pontos que importam para este guia: cada `agent()` pode receber uma **allowlist explícito de ferramentas**, os fluxos de trabalho gravam checkpoints e podem ser reanudados ou relançados, os subagentes podem ser isolados em contentor, e o contexto injetado por arquivos/extensões, bem como o *tool sulface* são mensuráveis e limitaveis. **0.24.7**, as ferramentas retardadas podem ser **lazy-loadés no Código de Modo** : `tools.eager` mantém apenas os esquemas necessários no pedido inicial, os outros
gravados e são descobertos através de `tool_search` → `tool_call`. A mesma libertação acrescenta uma **memória de chamada estruturada a pedido** e continua as sessões/workspaces sustentáveis. É uma implementação especialmente clara de `Select + Isolate` : remove os esquemas desnecessários do prefixo sem perder a capacidade de chamar a ferramenta mais tarde. A fundação de sandbox Linux apoia-se agora em `bwrap`. **Agente Equipe** y **Agente Arena** permanecem experimentais; Arena é especialmente útil para o benchmark privado, já que vários modelos podem receber a mesma tarefa em worktrees isolados. `/advisor` fornece um segundo parecer independente. OpenCode Outros empíricos: qualidade dos adesivos Scala, estabilidade com Metals, custo total e qualidade da gestão de licenças. Local Control deve permanecer
limitada a uma rede local de confiança.

A boa repartição dos papéis:

```text
Claude Code       = Opus 5.5/Sonnet 5.5 para raciocínio, depuração e microdesenvolvimento
Codex             = Sol 6.2/Luna para conduzir issues e para microdesenvolvimento com OpenAI
OpenCode/QwenCode = ambiente de execução para Qwen local, modelos via API e tarefas paralelas isoladas
Aider             = micro-diffs centrados no Git quando se quer um commit ou pequena correção por etapa
```

## Quando utilizado Aider

Use- o para:

* pequeno adesivo alvo;
* correcção de um teste;
* renome local;
* migração mecânica simples;
* modificação em que o diff Git é central;
* ciclo curto/teste muito curto.

Não utilize o medicamento para:

* arquitectura;
* legacy gordo;
* Bugs de múltiplos módulos;
* Refator profession profunda;
* decisão de design.

Aider é tanto melhor quanto respeita esta regra: ** adicionar poucos arquivos, dar um pedido precisa, verificar o diff, iniciar os testes seletivos**. Se adicionar demasiados arquivos, recriar o problema que você queria evitar: contexto caro, atenção diluído, diff mais amplo.

Se esta disciplina se importa menos do que o feedback LSP, OpenCode/Qwen Code podem cobrir melhor os mesmos casos, mas somente após a validação local em seu repo Scala.

## Comparativo sintético dos três arneses

| Critérios                 | Aider                            | OpenCode                              | Qwen Code                             |
|-------------------------|----------------------------------|---------------------------------------|---------------------------------------|
| Filosofia             | Diff Git-first, mínimo          | Agente generalista, sessões múltiplas | Agente do ecossistema alinhado Qwen          |
| Qualidade de diff (Scala) | Muito boa em pequeno scope       | Variável para medir em seu repo     | Variável para medir em seu repo     |
| Suporte LSP/Metals      | Não (repo map estático)          | Sim, parcialmente experimental.       | Sim; validar Metals na repo      |
| MCP                     | Não nativo                        | Sim.                                   | Sim.                                   |
| Local / BYOK            | Sim (todo compatível)   | Sim.                                   | Sim, ótimo com Qwen local          |
| Undo / rastreabilidade      | Excelente (um commit por passo) | Sessões, menos Git-centrado            | Períodos de sessões                              |
| Madurez Scala          | Probada em microdifs         | Prometida, não testada             | Harness maduro; qualidade Scala a medir |

A coluna decisiva não está no quadro: é ** a qualidade dos diffs no seu repo**, medida em dez tarefas reais com a grelha de métricas da secção 3. O quadro serve para saber o que testar, não para decidir.

## Exemplo: o comando de teste que qualquer arness deve receber

A alavanca número um da fivela lint/test é um comando comum, reprodutível e rápido. Não deduzcas `FooSpec` do nome `Foo.scala` : a continuação pode levar outro nome e um `testOnly` Sem provas selecionadas pode ter sucesso. Em CI limpo, `git diff HEAD` não vê os commits da PR. Assim, fixa uma **Base Git imutável** e compara-la com o candidato (merge base), tendo em conta todos os estados Git para o feedback local.

Exemplo `scripts/ai-validate.py` (Python) 3, Git, sbt ; adaptar `MODULES`, a política de caminhos e os relatórios JUNIT ao projecto). As suítes listadas devem cobrir todos os módulos de teste, incluindo os módulos de integração; uma suíte sem teste executada requer uma configuração explícita, não um sucesso silencioso.

```python
#!/usr/bin/env python3
"""Repository-specific example: adapt and protect the module map and policy."""
import argparse
import json
import re
import subprocess
import sys
import xml.etree.ElementTree as ET
from pathlib import Path

MODULES = {"api/": "api", "integration/": "integration"}
PROTECTED_NAMES = {"build.sbt", "plugins.sbt", "AGENTS.md", "CLAUDE.md", "CODEOWNERS", ".gitmodules"}
PROTECTED_DIRS = {".github", ".claude", ".codex", ".agents", "project", "migrations", "scripts"}
MAX_FILES, MAX_LINES = 20, 600


def git(*args):
    return subprocess.check_output(["git", *args])


def nul_paths(*args):
    return {p.decode("utf-8", "surrogateescape") for p in git(*args).split(b"\0") if p}


def changed_paths(base):
    # Union of committed, staged, unstaged and untracked paths; count renames as delete/add.
    return (nul_paths("diff", "--name-only", "-z", "--no-renames", base, "HEAD")
            | nul_paths("diff", "--cached", "--name-only", "-z", "--no-renames", base)
            | nul_paths("diff", "--name-only", "-z", "--no-renames", base)
            | nul_paths("ls-files", "--others", "--exclude-standard", "-z"))


def protected(path):
    parts = Path(path).parts
    return (bool(set(parts) & PROTECTED_DIRS) or Path(path).name in PROTECTED_NAMES
            or path.endswith(".sbt"))


def check_diff(base, head):
    # A final proof requires a committed candidate; never ignore untracked files.
    if git("status", "--porcelain=v1", "-z", "--untracked-files=all"):
        raise ValueError("Dirty candidate (including untracked files); inspect and commit authorized files first")
    raw = git("diff", "--raw", "-z", "--no-renames", base, head).split(b"\0")
    for metadata, raw_path in zip(raw[0:-1:2], raw[1:-1:2]):
        old_mode, new_mode = metadata[1:].split(b" ", 2)[:2]
        if {old_mode, new_mode} & {b"120000", b"160000"}:
            raise ValueError(f"Symlink or submodule requires separate review: {raw_path!r}")
    records = git("diff", "--numstat", "-z", "--no-renames", base, head).split(b"\0")
    count, lines = 0, 0
    for record in filter(None, records):
        added, removed, raw_path = record.split(b"\t", 2)
        path = raw_path.decode("utf-8", "surrogateescape")
        if protected(path):
            raise ValueError(f"Protected path requires separate human-approved policy: {path!r}")
        if added == b"-" or removed == b"-":
            raise ValueError(f"Binary change requires separate review: {path!r}")
        count += 1
        lines += int(added) + int(removed)
    if count > MAX_FILES or lines > MAX_LINES:
        raise ValueError(f"Diff exceeds policy: {count} files, {lines} lines")
    return {"files": count, "lines": lines}


def select_modules(paths):
    # Unknown/shared changes or no identified tests -> all declared test modules.
    if not paths or any(not any(p.startswith(prefix) for prefix in MODULES) for p in paths):
        return list(MODULES.values())
    return [module for prefix, module in MODULES.items()
            if any(path.startswith(prefix) for path in paths)]


def run_step(args, results):
    rc = subprocess.run(args, check=False).returncode
    results.append({"argv": args, "exit_code": rc})
    if rc:
        raise ValueError(f"Command failed ({rc}): {args!r}")


def verify_reports(prefix):
    # Adapt to actual report paths and frameworks; after clean, no stale reports.
    executed = 0
    for report in Path(prefix).glob("target/**/TEST-*.xml"):
        suite = ET.parse(report).getroot()
        if suite.tag != "testsuite":
            raise ValueError(f"Unexpected report format: {report}")
        if int(suite.get("failures", "0")) or int(suite.get("errors", "0")):
            raise ValueError(f"Failed tests in report: {report}")
        executed += int(suite.attrib["tests"]) - int(suite.get("skipped", "0"))
    if executed <= 0:
        raise ValueError(f"No executed tests proven for {prefix}")
    return executed


def main():
    parser = argparse.ArgumentParser()
    parser.add_argument("--base", required=True, help="Approved full Git commit SHA")
    parser.add_argument("--mode", choices=["targeted", "validate"], required=True)
    parser.add_argument("--sbt2", action="store_true")
    parser.add_argument("--receipt", type=Path, required=True)
    args = parser.parse_args()
    root = Path(git("rev-parse", "--show-toplevel").decode().strip()).resolve()
    receipt = args.receipt.resolve()
    if receipt == root or root in receipt.parents:
        parser.error("Receipt must be outside the repository")
    import os
    os.chdir(root)
    result = {"base": args.base, "mode": args.mode, "steps": [], "status": "FAILED"}
    try:
        if not re.fullmatch(r"[0-9a-f]{40}|[0-9a-f]{64}", args.base):
            raise ValueError("Expected a full immutable base SHA")
        head = git("rev-parse", "HEAD").decode().strip()
        base = git("merge-base", args.base, head).decode().strip()
        result.update(head=head, merge_base=base)
        if args.mode == "validate":
            result["diff"] = check_diff(base, head)
            modules = list(MODULES.values())
            # Full final validation, not a heuristic selection.
            run_step(["sbt", "scalafmtCheckAll", "compile", "Test/compile"], result["steps"])
        else:
            modules = select_modules(changed_paths(base))
        result["modules"] = modules
        test_task = "testFull" if args.sbt2 else "test"
        for prefix, module in MODULES.items():
            if module not in modules:
                continue
            # Explicit module suite: do not infer test names from source filenames.
            command = ["sbt", f"project {module}"]
            if args.mode == "validate":
                command.append("clean")
            run_step([*command, test_task], result["steps"])
            if args.mode == "validate":
                result.setdefault("executed_tests", {})[module] = verify_reports(prefix)
        if args.mode == "validate":
            if git("rev-parse", "HEAD").decode().strip() != head:
                raise ValueError("Candidate SHA changed during validation")
            check_diff(base, head)
            result["status"] = "PASSED"
        else:
            result["status"] = "FEEDBACK_ONLY"
    except (OSError, ValueError, subprocess.SubprocessError, ET.ParseError, KeyError) as exc:
        result["error"] = str(exc)
    finally:
        receipt.write_text(json.dumps(result, indent=2) + "\n", encoding="utf-8")
    print(json.dumps(result))
    return 0 if result["status"] in {"PASSED", "FEEDBACK_ONLY"} else 1


if __name__ == "__main__":
    sys.exit(main())
```

`--mode targeted` produz apenas feedback, embora os testes sejam verdes. Também inspecione os ficheiros não seguidos e as alterações locais. Se não for identificado nenhum módulo fiável, executa todas as suites declaradas. Em um edifício real, estende a selecção aos viciados em choques (por exemplo, api → integração; o fallback continua a ser todas as suites quando o impacto é incerto. `--mode validate` requer um candidato committado e um worktree limpo, controla o diff completo, executa as suites completas após `clean`, verifique os relatórios de testes, o SHA e a limpeza final. Rejeite os caminhos protegidos, binários, symlinks e alterações do subsistema por defeito; toda excepção é uma decisão humana numa política de validação separada e aprovada, nunca um argumento de bypass dado ao writer.
`--sbt2` usar `testFull` em vez de `test` para uma execução completa em sbt 2.x. O programa é um exemplo de arness para adaptar e testar; o escore exato da spec e as excepções devem ser comprovados por um humano ou um allowlist de caminhos aprovado independentemente. Não cobre por si só todos os edifícios Scala, os subcomponentes, os testes fora de Junit ou os ficheiros ignorados. CI deve executar num checkout isolado e limpo, com a política de confiança (secção 15A). O relatório JSON e o certificado inviolável não é confundido.

Wrapper `scripts/ai-test-changed` (ejecutável, partilhado por Aider, Codex e Claude)

```bash
#!/usr/bin/env bash
set -euo pipefail
: "${AI_BASE_SHA:?Set the approved base commit SHA first}"
repoRoot=$(git rev-parse --show-toplevel)
receiptDir=$(mktemp -d)
printf 'Local feedback receipt: %s\n' "$receiptDir/validation.json"
exec python3 "$repoRoot/scripts/ai-validate.py" --base "$AI_BASE_SHA" \
  --mode targeted --receipt "$receiptDir/validation.json" "$@"
```

No início, fixa `AI_BASE_SHA` na revisão aprovada (não a `HEAD` revalorada após cada commit). Por exemplo, no worktree de tarefas:

```bash
export AI_BASE_SHA="$(git rev-parse origin/main)"
aider --test-cmd "./scripts/ai-test-changed"
```

Antes de empurrar a PR, em um candidato limpo e committado:

```bash
receiptDir=$(mktemp -d)
python3 scripts/ai-validate.py --base "$AI_BASE_SHA" --mode validate \
  --receipt "$receiptDir/validation.json"
```

Mantenha o teste estruturado no pacote de revisão (base, base de merge, SHA candidato, pedidos, códigos de devolução, número de testes executados e estado). Se a validação não estiver disponível, falha ou se refere a outro SHA, não declara "Done Done". Os próprios programas de validação requerem testes: saída sbt não- zero sem `[error]`, umtracked, commit já criado, ficheiro renomeado para uma rota proibida, relatório ausente/vacío, SHA alterado. Executa estes casos em um repo temporário e um sbt Simulado antes de promover a política. Estes exemplos foram testados com um depósito Git temporaire et un sbt Simulado; isto valida a lógica dos scripts, não os comandos sbt Os checks end-to-end estão pendentes de execução em CI.
