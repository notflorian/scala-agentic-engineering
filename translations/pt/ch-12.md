#### Comandos worktree concretos para o fluxo de trabalho multiagente

O worktree isola os arquivos de trabalho e o índice para dois writers, **no suas permissões**. Codex agora pode criar e retomar seus worktrees nativamente; os comandos Git em seguida mantêm-se a **procedimento portátil e explícito**, independente do arness:

<!-- section: s-2 -->
# 1 Criar um worktree para uma tarefa específica

`git worktree add ../project-feature-x -b feature/task-x main`

<!-- section: s-3 -->
# 2 Criar um worktree para a revisão (leitura única)

`git worktree add --detach ../project-review-x "$headSha"`

Recupera previamente o SHA exato da PR; comunica também o SHA de base e calcula a merge base. Não verifique `HEAD` de `main` por defeito.

# 3. Listar os programas activos

`git worktree list`

<!-- section: s-5 -->
# 4. Trabalhar no worktree (sandbox separado a configurar)

`cd ../project-feature-x`

<!-- section: s-7 -->
# 5. Verificar o estado do repo principal

<!-- section: s-8 -->

# Script utility: scripts/ai-worktree.sh

```sh
#!/usr/bin/env bash
# Usage: ./scripts/ai-worktree.sh create|list|remove|merge <name> [base]
set -euo pipefail
ACTION="${1:-list}"
NAME="${2:-}"
BASE="${3:-main}"
if [[ "$ACTION" != "list" && ! "$NAME" =~ ^[a-zA-Z0-9][a-zA-Z0-9._-]*$ ]]; then
  echo "Invalid worktree name" >&2
  exit 1
fi

case "$ACTION" in
  create)
    BRANCH="agent/${NAME}"
    DIR="../$(basename "$(pwd)")-${NAME}"
    git worktree add "$DIR" -b "$BRANCH" "$BASE"
    echo "Worktree créé : $DIR (branche $BRANCH)"
    echo "cd $DIR && claude"
    ;;
  list)
    git worktree list
    ;;
  remove)
    DIR="../$(basename "$(pwd)")-${NAME}"
    git worktree remove "$DIR" # Refuses dirty worktrees
    git branch -d "agent/${NAME}" # Refuses unmerged branches
    echo "Worktree supprimé : $DIR"
    ;;
  merge)
    echo "Merge through the reviewed PR and required checks." >&2
    exit 1
    ;;
esac
```

Regras de segurança worktree:

- Um worktree = um agente = uma tarefa. Nunca dois agentes no mesmo worktree.
- O worktree principal (mano) é reservado para o humano e o CI.
- Qualquer agente de trabalho deve ser criado a partir de um ramo próprio (no WIP).
- A merda de um worktree agente passa através de uma revisão humana.
- Limpa os worktrees depois da merda: um worktree órfão é dívida.

**Aislamento efetivo.** Um worktree compartilha os refs e parte da configuração Git, bem como os crédentials/casas da conta de usuário se nada os separa. Da a cada agente um sandbox com raízes de escrita explícitas, uma pasta temporária, ferramentas MCP em menor privilégio e segredos separados; para código não confiável, prefere um contentor/VM sem montagem de `$HOME` Sem socket Docker nem chaves de produção. Em local, rejeita o full-access / bypass; lado Codex Configure sandbox e avales, lado Claude sandbox e permissões allow/deny, e depois teste tentativas de escrita fora do perímetro e acesso à rede proibido. Os hooks são sinais/controles complementares, não uma fronteira de contenção.

| Função | Direitos efectivos |
|------|------------------|
| Researcher / reviewer | Leitura de depósito ; não push ; scratch isolado se teste de reprodução |
| Writer | Escrita em seu sandbox e ramo de trabalho; push somente autorizado |
| Steward | Correcções no PR explicitamente transferidas; nunca merge / force-push |
| CI não confiável | Checkout, compile, testes; token leitura, nenhum segredo privilegiado |
| Release pipeline | Identidade e segredos dedicados ao meio ambiente, após gate humano/político |

Separa o acesso de rede e tokens GitHub por papel; não dá os credentials de implantação ao agente. Os comentários do PR, logs e arquivos não confiáveis são dados, não novas permissões.


O fluxo de trabalho seguro:

```text
worktree A : writer choisi par la nature de la tâche
worktree B : l’autre famille peut expérimenter ou reviewer
diff final : humain arbitre
review : modèle indépendant no-write
tests : CI / IntelliJ / sbt
```

### Paralelismo entre resultados e WIP

Para um desenvolvedor só, começa com dois User Stories independentes como máximo, incluindo os PR em revisão. Um writer Codex e um writer Claude podem avançar em ramos separados; cada um fornece a outro um pacote de revisão fresco. Declara as dependências, módulos/arquivo partilhados, contratos e ordem de integração antes de começar. Os stories que modificam uma mesma invariante ou migração devem ser sequestrados; só a sua exploração read-only pode ser paralela. Tente-se e reconvalida após cada merge. ## Exploiter a review Codex Em máquina: descodificação tipográfica

Com a classificação de gravidade da secção 5 (etapa) 7) e do ADT `ReviewResult` da secção 7B, uma saída Codex ** uma vez classificada e documentada** converte-se num dado explorável por um gate de merge em vez de um texto para releer. As verificações brutas do modelo permanecem numa fase de classificação: apenas um teste, uma regra determinista ou uma decisão humana os promovem no gate.

```scala
import io.circe.parser.decode
import zio.*

object CodexReviewGate:

  def parse(raw: String): IO[LlmError, ReviewResult] =
    // Les modèles entourent parfois le JSON de ```json ... ``` malgré la consigne — nettoyage défensif
    val cleaned = raw.replaceAll("(?s)```json|```", "").trim
    ZIO.fromEither(decode[ReviewResult](cleaned))
      .mapError(e => LlmError.Decode(s"Sortie Codex non conforme : ${e.getMessage}"))

  // Le gate ne reçoit que des findings préalablement validés :
  // BLOCKING et REGRESSION_RISK doivent être vides (ou contestés explicitement).
  def gate(review: ReviewResult): IO[String, Unit] =
    val blocking = review.findings.filter(f =>
      f.severity == Severity.Blocking || f.severity == Severity.RegressionRisk
    )
    ZIO
      .fail(
        blocking
          .map(f => s"[${f.severity}] ${f.file} — ${f.message}")
          .mkString("Retours à traiter avant merge :\n", "\n", "")
      )
      .when(blocking.nonEmpty)
      .unit
```

Note a simetria com o princípio orientador: o ser humano continua a ser o árbitro (pode contestar um `BLOCKING`), mas o caminho por defeito é determinista. Uma saída Codex não parsable faz fracassar o gate, um revisor que não respeita o formato acordado não valida nada.

## GitHub Copilot : camada GitHub-nativa, não terceira revisão profunda

Se o descanso mora em GitHub, Copilot traz um valor complementar a Claude Code y Codex **a nível do fluxo de trabalho GitHub**não como terceiro gato generalista em IntelliJ. La **GitHub Copilot app** Adicione uma vista a My work para navegar pelos resultados e PR, iniciar uma sessão de um resultado, examinar os checks, solicitar a correção de um comentário ou uma CI vermelho e, se você o permitir, pilotar a aterragem da PR. Use esta superfície como controle plano GitHub ; guarda IntelliJ + Claude Code para implementação local exigente e Codex para a revisão independente.

```text
Issue GitHub bien spécifiée
→ Copilot coding agent possible pour une petite tâche bornée
→ PR
→ CI déterministe
→ Copilot Code Review automatique
→ Codex Terra / Sol si review profonde nécessaire
→ humain
```

Usos onde o Copilot é realmente útil:

```text
✅ parcourir et prendre en charge des issues depuis GitHub ;
✅ déléguer une petite issue bien bornée à un coding agent ;
✅ créer / suivre une PR et ses checks ;
✅ reviewer automatiquement les nouvelles PR ou les nouveaux pushes ;
✅ proposer des corrections depuis les commentaires de review ;
✅ exploiter AGENTS.md, instructions GitHub, skills et MCP dans la review ;
✅ compléter CodeQL / Code Quality par un signal LLM GitHub-native.
```

Usos em que se volta sobre tudo redundante:

```text
❌ architecture ou bug Scala difficile déjà traité par Opus 5.5 ;
❌ troisième review manuelle systématique après Codex Sol 6.2 ;
❌ deuxième writer sur la même branche pendant qu’un agent principal travaille ;
❌ remplacement de sbt, tests, mutation testing, CodeQL ou review humaine.
```

**Copilot Code Review é um sinal, não uma gate de aprovação.** Uma revisão Copilot é publicada com o estado `Comment`, não `Approve` ou `Request changes` ; portanto, não conta como aprovação necessária e não bloqueia a merge por si só. É um bom lugar para uma revisão automática pouco friccional, enquanto Codex continua a ser o revisor independente iniciado voluntariamente sobre as mudanças não triviais ou riscosos.

A regra da concorrência continua a ser a mesma que para todos os agentes: se Copilot nuvem agente aplicar um adesivo, Claude Code e Codex não devem escrever simultaneamente no mesmo ramo. Use uma delegação clara, ou um worktree / um ramo separado, e depois faz com que o diff arbitre pelo humano.

## Claude Ship: Automatizar o post-PR, não a responsabilidade da mermelada

**Claude Ship** é uma camada GitHub pós-implantação, independente do coding agente que produziu a PR. Divida-se em três responsabilidades: encontrar defeitos, aplicar correcções e avaliar uma política de aprovação. Não confundir com um novo modelo, nem com `/code-review` ou Ultrareview (revistas a pedido).

| Superfície | Função | Acesso / Consumo |
|---------|------|----------------------|
| **`/ship`** | Commit/push, abertura do PR se necessário, revisão local e depois vigilância dos checks e retornos | Claude Code local; uso normal da sessão |
| **`/steward`** | Supervisão e correção de um PR já aberto, sem revisão inicial | Claude Code local; uso normal da sessão |
| **Código de revisão** | Revisão estática multi-agente, verificação e classificação de findings, comentários inline e check | Team/Enterprise; créditos de uso; GA |
| **PR Steward** | Correcções de CI, conflitos e feedback , commits no ramo e relatórios de mudanças | Team/Enterprise; créditos de uso; beta- |
| **Claude Approvals** | Avaliação da `.claude/approvals.yml`, verificação e possível aprovação GitHub | Team/Enterprise; classificadores e revisãos ativados facturados; beta- |

O serviço de organização atua através da Claude GitHub App, sem necessidade Claude Code Não está incluído em Claude Max e não está disponível com ZDR, a configuração HIPAA ou as chaves CMEK. Os comandos locais atuam com suas próprias identidades Git/GitHub. Verifica sua presença após atualizar a Claude Code, avec `gh auth status` e um clone local GitHub. A referência detalhada dos pedidos está vinculada nas fontes.

### Workflow apenas: `/ship` ou `/steward` com Codex e Claude Code

```text
Writer Codex ou Claude → spec satisfaite + tests locaux verts
→ vérifier le diff, les fichiers non suivis et les secrets avant tout push
→ ouvrir la PR ; /ship si tu veux aussi une review Claude locale
→ /steward si la PR est déjà ouverte et que seule la surveillance est utile
→ correctifs mécaniques bornés → stop de la surveillance
→ review indépendante de l'autre famille sur le SHA final
→ CI verte → humain : merge
```

Para o seu uso Claude Max + Codex, primeiro teste `/steward` numa pequena PR: evita repassar uma revisão inicial se o Opus/Sol já a tiver feito. Se Claude tiver escrito ou corrigido o código, guarda Codex como repassar independente. Codex escreveu e que Claude também aplicou as correcções, exige uma revisão fresca das correcções por parte de Codex e relee todo o diff; dois modelos que foram produzidos não constituem automaticamente dois acórdãos independentes.

** Cuidado! `/ship` :** o comando pode fazer alterações não committadas, incluindo ficheiros não seguidos, e empurrar sem confirmação interativa bloqueada. Não tem a detecção de nomes de ficheiros sensíveis para proteger o conteúdo. `git status`, o diff staged e umstaged, os novos ficheiros, a digitalização de segredos e o remoto antes de o invocar. Prefire um ramo dedicado e um worktree cujo conteúdo já está validado.

A supervisão local pode executar o código recuperado a partir do GitHub com os seus direitos: apenas activa o código num repositório e um ramo com um contribuinte autorizado de confiança. Não deixe que um comentário do PR amplie a spec ou permissões. Use um ambiente sem segredos de produção, e pare o ciclo com `/ship stop` (ou interrupção da sessão) antes de intervir no mesmo ramo. As restrições nativas das acções sem mensagens de utilizador não substituem as regras GitHub ou as salvaguardas locais.

### Workflow equipe: adoção progressiva, não três agentes obrigatórios

- **Code Review** : começa com `Standard`, `Quick` para as mudanças de rotina, `Deep` para depósitos críticos. Anthropic escolhe os modelos; estes níveis não são os esforços de Opus. Configuração `REVIEW.md` para os invariantes Scala e a gravidade dos findings; a revisão lê as regras do ramo de base ou por defeito, não as propostas pela PR. Não compila nem executa o código e o seu check não constitui um veto sobre a merge.
- **PR Steward** : começa no modo manual (`@claude steward`) com um único depósito piloto e um limite de despesas. Escreva no ramo sem pedir para cada correcção e trata também os reembolsos de bots. Excluir da sua delegação as mudanças de arquitetura, conflitos semânticos, migração e arquivos críticos. `@claude stop` ou a retirada do rótulo `claude-pr-steward-watching` Parar a supervisão da PR.
- **Claude Approvals** : começa em `mode: observe` A política vem do ramo predefinido, combina as regras mais rigorosas e pode usar rotas, fatos de PR e classificadores. `.claude/approvals.yml`, `REVIEW.md`, `CODEOWNERS` e os fluxos de trabalho CI como arquivos críticos. Ver os limites de aprovação na secção 15A.

Para um PR Scala, limita o steward a uma correção de lint, um import, um erro de compilação local ou um finding reproduzido. Pare após dois fracassos idênticos, qualquer desvio ao escore ou qualquer necessidade de modificar um invariante. Nunca peça que devolva a CI Verde enfraquecendo um teste, uma aseveração ou um check. Um conflito que afeta uma regra profissional não é uma correção mecânica. Estas regras são o seu protocolo operacional: devem ser controladas independentemente, não supostamente garantidos pelo serviço.

**Claude Ship vs Copilot:** O serviço Claude pode ser relevante para o volume em equipa; em solitário, os comandos locais e a revisão cruzada existente evitam uma nova assinatura e revisões redundantes. Medição em PR comparáveis: minutos humanos até a merge, custo total (revisiones, correções, CI), findings realmente úteis, adesivos fora do escore, número de pushes, defeitos escapados e reverts. Os ganhos de volume e reverts anunciados por Anthropic sobre suas próprias pausas referem-se a um processo completo, não um efeito causal isolado de Claude Ship nem um teste específico a Scala.

## Equivalente Codex de Claude Ship: revisão, correção e vigilância

Codex cobre as mesmas necessidades por várias primitivas, sem impor uma série de agentes pós-PR. Não confunde revisão, autorização de escrita e autorização de merge.

| Necessidade | Claude | Codex |
|--------|--------|-------|
| Preparar e abrir um PR | `/ship` | Em breve de finalização: testes → `/review` local tão útil → commit/push → PR. |
| Vigiar um PR existente | `/steward` | **Goal mode (`/goal`)** ou **Heartbeat** ; tarefa Codex Cloud para execução alojada |
| Revisão GitHub | Code Review | **Codex Code Review** : `@codex review` ou ativação automática |
| Corrigir um finding ou um fracasso CI | PR Steward | `@codex fix the P1 issue`, `@codex fix the CI failures` ou objectivo Codex limitado |
| Monitorização persistente / automação alojada | PR Steward | Codex Cloud (tareia borneia), eventos GitHub (seguimento parcial); GitHub Acção se orquestração CI dedicada |
| Revisão de segurança dedicada | Revisão especializada | `@codex security review` (segundo o seu direito) |
| Política de aprovação | Claude Approvals | GitHub Rulesets, CODEOWNERS e required checks; equivalência parcial |

### Goal mode, Heartbeats e Codex Cloud: equivalente funcional de `/steward`

Privilegia as primitivas nativas mantidas por OpenAI em vez da antiga skill de vigilância retirada do depósito Codex e seus forks comunitários. Permitem construir um ciclo pós-PR sem programa Python arquivado, plugin de terceiros ou chave. API OpenAI adicional com uma conta ChatGPT Não é um serviço PR Steward idêntico ao deAnthropic: a vida útil, os disparadores e as escrituras. GitHub dependem do arnês, das permissões e do plano. **GPT‑6.2 Sol Medium** É o modelo de referência para esta missão; a escolha do modelo não cria por si só uma supervisão permanente.

| Superfície | Mecanismo recomendado | Limite operacional |
|---------|----------------------|-----------------------|
| Codex Desktop / CLI / extensão IDE | `/goal` com critérios de saída verificáveis | Sessão e ambiente disponíveis; posto acordado para o trabalho local |

#### Goal modo: objetivo persistente e verificável

`/goal <objective>` Aporta o objectivo e os critérios de suplementação à sessão. `/goal` mostra o objectivo; `/goal edit`, `/goal pause`, `/goal resume` e `/goal clear` permitem modificar, suspender, retomar ou retirar. Em Desktop, usa os controlos de progressão. Para código Scala local, mantenha o mesmo worktree e os testes da spec; não novo writer em paralelo. O modelo deve poder verificar a CI e as devoluções publicadas em GitHub com as ferramentas realmente disponíveis.

Gabarit para um PR existente, após autorização do push em seu ramo (GPT‑6.2 Sol Medium):

```text
/goal Bring the current pull request to a verified, merge-ready state.

Use the approved spec and AGENTS.md. Confirm the PR URL, base branch, head branch and initial SHA.
Monitor GitHub required CI checks, mergeability and published review feedback. Before each action,
refresh the PR state and verify its head SHA. Stop on unexpected changes or concurrent writers.

Fix only verified branch-related failures and actionable findings within the approved scope.
Resolve conflicts only when the intended behavior is unambiguous. Keep diffs minimal.
Never weaken tests, assertions, security checks or CI requirements. Do not change public contracts,
dependencies, build configuration, workflows or database schemas without explicit approval.
Retry clearly transient failures at most three times; never patch unrelated flaky tests or infrastructure.
After each fix, run the required targeted checks, commit and push only to the authorized PR branch.
Reassess required checks and review feedback on the new SHA; require independent review of the final diff.
Never approve, merge, force-push, or reply to human reviewers or resolve their threads without authorization.

Stop when required checks pass on the latest SHA, no actionable findings or conflicts remain,
and independent review or human approval is the only remaining gate. Stop also if the PR closes,
permissions are missing, the scope must expand, the same root cause fails twice, or 60 minutes elapse.
If checks are still pending or unavailable, report them as such; do not claim the PR is ready.
Finish with a concise report in French containing the PR URL, final SHA, CI status, fixes pushed,
independent review status, unresolved findings and blockers.
```

A duração de 60 minutos e os contadores são limites da missão propostos, não timeouts garantidos pelo produto. Interromps ou pausa o goal se necessário; não confunde o objetivo alcançado a aprovação da mermelada.

#### Heartbeats: seguimento recorrente sem sessão de raciocínio contínuo

Os Scheduled Tasks num chat (Heartbeats) reutilizam o seu contexto e permitem intervalos curtos em minutos. OpenAI documenta o caso de seguimento de uma PR e tratamento de novas devoluçãos. Prefire este mecanismo se o tempo de espera CI dominar o trabalho: um breve reinício num evento novo em vez de um ciclo de raciocínio permanente. Uma retomada não é gratuita. No local, o posto deve permanecer ligado e a aplicação Desktop activa. Primeiro teste uma execução manual, e depois verificar em Scheduled o modelo, o esforço, o sandbox, as permissões e as condições de parada. Não supõe que o rápido possa desactivar a tarefa: verifique o seu estado e desativá- la manualmente se necessário.

Gabarita para enviar o gato Codex PR (sem Goal Mode Active):

```text
Create a recurring follow-up in this conversation every 10 minutes for the current GitHub pull request.
Use GPT-6.2 Sol Medium if selectable. Keep the same approved spec and AGENTS.md constraints.
Confirm the PR URL, authorized branch, initial SHA, available GitHub tools and schedule before writing.

At each run:
- Refresh the head SHA, required checks, mergeability and published review feedback.
- Deduplicate by repository, PR, SHA and finding/check ID. If nothing actionable changed, return briefly.
- Stop on unexpected branch changes, concurrent writers, unavailable permissions or out-of-scope findings.
- Fix only verified branch-related failures and actionable authorized findings. Run targeted tests,
  commit and push only to the PR branch. Recheck the new SHA.
- Preserve all validation requirements and public contracts. No unrelated refactors, CI or dependency changes.
- Retry transient failures at most three times in total; stop after two failed fixes for the same root cause.
- Never approve, merge, force-push or interact with human review threads without authorization.

Keep a record of the run count, latest SHA, handled findings and retry counts across runs.
Stop and disable the follow-up when required checks pass on the latest SHA, there are no conflicts or
remaining actionable findings, and only independent review or human approval remains; also stop if the PR
closes, human help is needed, six runs have completed, or 60 minutes have elapsed.
If automatic disabling is unavailable, report that the schedule must be disabled manually and perform no more edits.
Report meaningful changes only, in French; include the final PR URL, SHA, checks, fixes and blockers.
```

#### Codex Cloud: mesmo contrato, execução alojada

Para trabalhar Mac desligado, usa um ambiente Codex Cloud publicado (secção 12) com o depósito, o JDK, sbt, ferramentas de teste e acesso GitHub Reverr em uma primeira tarefa não crítica o ramo alvo, a leitura dos checks/logs e reviews, as permissões de push e, se necessário, de CI. Um conector GitHub ou a presença de `gh` não garante por si só esses direitos. Use os segredos geridos e os domínios de rede autorizados, não token no rápido ou no repo. Não confunde o ambiente reutilizável com a tarefa isolada que se realiza lá, nem a possibilidade de continuar sem o posto com uma garantia de vigilância indefinida.

Para um PR existente, selecione GPT‑6.2 Sol Medium e repete completamente o prompt Goal Mode anterior ** sem o prefixo `/goal`** se o cliente Cloud não apresentar o pedido. Para completar um User Story antes desta vigilância, adicione este preâmbulo (em Cloud ou no chat local antes de lançar o goal):

```text
Finalize the current implementation against the approved spec and AGENTS.md.
Run the required build, formatting and targeted tests. Review the diff for correctness, regressions and scope.
Check staged, unstaged and untracked files, secrets and the remote before committing.
Commit, push and create or update the PR only if authorized. Report the URL and head SHA.
Then apply the bounded PR stewardship objective below in the same authorized environment.
If direct push or PR creation is unavailable, report the exact blocker and the validated patch; do not claim success.
```

Se a tarefa Cloud atingir o seu limite antes da CI verde, volta ao mesmo chat com o SHA e o estado dos checks; não cria várias tarefas concorrentes no mesmo ramo. Não é necessário nenhum programa externo ou plugin da babá para este contrato. As permissões, limites de execução e direitos de escrita ficam por validar.

#### Rolamento e paragem do ciclo

```text
Triage ou correction mécanique isolée → GPT‑6 Luna High
Stewardship end-to-end                → GPT‑6.2 Sol Medium (Sol 6.1 Medium en fallback)
Root cause difficile / conflit subtil → GPT‑6.2 Sol High, après requalification de la cause
Limite de capacité prouvée            → Astra Light si disponible, sur contexte propre
```

Não mobilize nem Ultra nem Ultrafast por defeito: a espera CI é essencialmente sequencial. Medição do número de vezes, pushes, minutos humanos e consumo até a mermelada. Um estado verde em um antigo SHA não demonstra nada sobre a versão atual; após a correção, requer os checks e a revisão independente do diff final.

### Claude Code Cloud Auto-fix: stewardship evento solo

O Auto-fix é diferente de Claude Ship PR Steward (Team/Enterprise). Na Claude Code Cloud, o agente percebe os eventos. GitHub do PR (ajedrez) CI, reviews/comentários) e pode empurrar um adesivo quando este é claro. Não há lugares locais que deixam a ignição. O seguimento entra dentro dos limites Claude Code do plano compatível , a instalação da Claude GitHub App no requiretory é necessário.

Para uma PR criada na nuvem, ativa Auto-fix no menu da PR do cartão Changes. Desde o CLI local no ramo PR, `/autofix-pr` detecta a PR através de `gh`, abre uma sessão na nuvem e ativa o seguimento. Para uma PR existente (incluindo a escrita por Codex), dá o seu URL a uma sessão Claude Cloud e pede o auto-fix. Para o rastreamento através do menu Auto-fix ou pedindo a Claude para parar de vigiar a PR.

**Límites importantes:** GitHub não notifica automaticamente a Auto-fix de um conflito causado pelo avanço da base; inspeciona a mergeabilidade e pede uma base explícita se necessário. Claude pode responder aos threads abaixo da sua conta (resposta notificada como agente) ; em qualquer caso, automação `issue_comment` que poderiam desencadear uma operação privilegiada. Não active Auto-fix num depósito onde um comentário possa activar uma implantação ou uma operação infra sem gate externa. As instruções de duração e paragem no prompt não são um corta-circuito do sistema garantido; verifique a desactivação efectiva no fim.

Prompt para a sessão Claude Cloud:

```text
Enable Auto-fix for [PR_URL] only after verifying branch ownership and the approved specification.
Monitor published review feedback and CI failures. Fix only verified, in-scope, branch-related defects.
Never weaken tests, assertions, CI or security controls. Do not change protected files or public contracts.

Commit and push authorized minimal fixes only. Never force-push, approve or merge.
Do not post or resolve human review threads without explicit authorization.
Stop and report ambiguous findings, conflicts, permission problems, two failed correction cycles
for one root cause, or exhaustion of the agreed time budget.
When the final SHA has green required checks and no actionable findings, disable Auto-fix and verify it stopped.
Report in French the final SHA, CI evidence, changes and blockers.
```

### Transferência de ownership e roteamento dos stewards

| Writer | Reviewer independent | Steward por omissão |
|--------|----------------------|-------------------|
| Codex local | Opus 5.5 Medium | GPT‑6.2 Sol Medium, Goal ou Heartbeat |
| Codex Cloud | Opus 5.5 Medium | Codex Cloud, objetivo limitado |
| Claude Code local | GPT‑6.2 Sol Medium | Claude `/steward` |
| Claude Code Cloud | GPT‑6.2 Sol Medium | Cloud Auto-fix |

Uma PR pode passar para o outro fornecedor se o seguimento nativo for mais adequado para isso. Transfere explicitamente `repo + PR + branch + head SHA + base SHA + spec + findings autorisés + permissions + budget + conditions d'arrêt`. Pare o watcher, Heartbeat, Goal, Auto-fix e as tarefas corretivas existentes antes de autorizar o novo writer; verifique a ausência de sessão concorrente e o estado remoto antes de cada push. Uma mudança inesperada de SHA interrompe o trabalho. Não reutiliza um velho worktree como fonte de verdade. Após a transferência, o steward é o autor das correcções: continua a ser necessária uma nova revisão independente das alterações e dos testes sobre o SHA final.

**Eleção individual:** se Codex escrito, Opus reviewe e Codex toma as correcções através de Goal mode, Heartbeat ou Cloud (GPT‑6.2 Sol Medium) se necessário; se Claude escreve, Codex reviewe e Claude retomam via `/steward` ou Cloud Auto-fix. Após qualquer correção, revalida as mudanças no SHA final com a outra família e os checks deterministas. Não acumula sistematicamente Codex Code Review, Claude Code Review, Copilot e uma revisão local: um único fluxo automático por defeito, uma revisão independente proporcionada ao risco, um único writer corretivo e depois o humano árbitro.

## Nota de posicionamento: A2A frente a MCP

O Protocolo **A2(Agente-to-Agente)**, iniciado pelo Google e confiado à Linux Foundation, padroniza a comunicação *entre agentes* de fornecedores diferentes (descubrimento de capacidades, delegação de tarefas, acompanhamento da execução), onde MCP padronização da comunicação *agente ↔ Ferramentas*. Pelo fluxo de trabalho deste guia, o veredicto de junho 2026 é simples: **A2A não traz nada a um dev sozinho.**A orquestra Claude ↔ Codex Descripto aqui passa pelo humano (e é uma featura: filtram-se os retornos), e os subagentes. Claude Code Eles têm seu próprio mecanismo nativo. A.2É pertinente se uma organização industrializa agentes heterogêneos (um agente Claude que delega formalmente em um agente) Codex Alojado em outra parte) ? em cujo caso, reavaliar a maturidade do protocolo e de suas implementações nesse momento, não antes.
