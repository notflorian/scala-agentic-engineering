## Para comprimir com RTK / Headroom

* logs CI;
* saídas `sbt test` longas;
* gordo `git diff` ;
* `rg` maciço;
* JSON voluminoso;
* documentação longa;
* Listings de Ficheiros.

## Não comprimir agressivamente

* Código- fonte a ser alterado;
* Testes críticos;
* `build.sbt` ;
* migração;
* stack rastros Scala complexos;
* erros de implicits/givens;
* Contratos JSON públicos.

As cinco alavancas de custo cumulativas são: roteamento para modelos baratos, compacção do contexto, prompts scopées com rotas de arquivo, prompt caching e Batch API quando adaptado.

> **Context rot.** Não confunde três limites diferentes:
>
> ```text
> capacité physique     = combien de tokens entrent dans la fenêtre ;
> récupération          = le modèle retrouve-t-il encore l'information pertinente ;
> raisonnement utile    = sait-il encore l'appliquer correctement parmi tout le reste ?
> ```
>
> Literatura 2026 mostra que as duas últimas podem se degradar gradualmente **Mucho antes** saturação
> física. Na mesma tarefa, adicionar contexto desnecessário pode reduzir a qualidade mesmo quando a informação relevante
> Os sintomas típicos de uma longa sessão de agente são: limitações antigas menos
> , revestimentos de hipóteses já refutadas, releitura repetida dos mesmos arquivos, fivelas de correção e abandono
> Apesar das informações suficientes.
>
> Portanto, uma transcrição longa não é uma melhor memória. Em uma sessão de código também acumula `rg`, saídas.
> MCP,
> O **working set decision** deve:
> permanecer pequeno:
>
> ```text
> objectif + contraintes + plan + décisions + diff courant + preuves essentielles
> ```
>
> A compaction (`/compact`) continua sendo uma compressão com perdas: ocorre após a acumulação e pode
> Resumindo um invariante discreto, uma hipótese refutada ou um detalhe raro. **Não a trate como um mecanismo normal de
> Depois.** Para uma tarefa importante, prefere um handoff explícito e controlado (`HANDOFF.md` ou ficheiro de estado,
> O desfile estrutural continua sendo o **aislamento na parte superior** : delegar a exploração voluminosa,
> logs, testes, documentação e pesquisas independentes a subagentes com seu próprio contexto,
> E depois só tira conclusões curtas e cegas.
>
> ```text
> 100K tokens explorés dans un worker
> → 1–2K tokens de résultat
> → parent propre pour décider et écrire
> ```
>
> Esta regra também se aplica à revisão: **no dá a Codex a transcrição completa de uma longa sessão Claude**.
> Dê uma janela fresca com `spec + diff final + fichiers modifiés + tests + invariants`. Você consegue ao mesmo tempo.
> isolamento de modelo e isolamento de contexto.

Para a cache explícita OpenAI, raciocina no custo total: uma escrita para 1,25× sem nenhuma reutilização custa mais do que uma chamada normal. Com pelo menos uma reutilização do mesmo prefixo durante a vida útil da 'cache', uma escrita e depois uma leitura a 0,1× custo 1,35× no total contra 2× sem cache. Portanto, ativa um breakpoint apenas para um prefixo estável cuja reutilização é provável, e mede por separado tokens escritos, tokens lidos, taxa de hit e invalidações.

## As quatro estratégias canônicas do context engineering

A disciplina foi formalizada para o fim 2025 sob o nome de **context engineering** Definição Anthropic: • todas as estratégias para curar e manter o conjunto ótimo de tokens durante a inferência • formulação Karpathy: • preencher a janela de contexto com a informação correta para o próximo passo • A taxonomia de referência (LangChain) distingue quatro estratégias, que este guia prático já separado • as nomeia para verificar que nenhuma se esquece:

| Estratégia    | Pergunta                                      | Aplicação deste guia                                                                                      |
|--------------|-----------------------------------------------------|------------------------------------------------------------------------------------------------------------------|
| **Write**    | O que tem que sobreviver fora da janela?    | `AGENTS.md`, `MIGRATION_STATE.md`, auto-memory, registros de tarefas, registro de dívidas                            |
| **Select**   | O que entra na janela, e quando?     | Sourcebot / ScalaSemantic / Codebase-Memory / rg / Metals MCP, recuperação justo a tempo                        |
| **Compress** | O que pode perder Tokens sem sinal?  | RTK / Headroom em logs e diffs, saídas truncadas, handoff estruturado; `/compact` apenas como último recurso. |
| **Isolato**  | O que deve viver numa janela separada? | Subagents read-only, worktrees, reviewer no-write, sessions distinct por work                                 |

Duas regras operacionais resultantes desta tabela e que o resto do guia não abrange explicitamente:

- ** Progressive disclosure of instruments** : cada servidor MCP adiciona os seus esquemas de ferramentas à janela de cada sessão. Limita os servidores e ferramentas ativados por agente (oACP d'IntelliJ e Claude Code o permitem) e prefere a descoberta à procura MCP de agosto 2026 por outro lado, a *progressivo discovery* catálogos de ferramentas uma prioridade do protocolo. Num catálogo grande, **Jev pode servir de pré-selector** : escolher alguns skills/instrumentos candidatos antes de carregar as suas definições no contexto do LLM.
- **Compasão como decisão, não como reflexo** : pontuação Jev pode informar `topic_shift` ou `old_context_still_needed`, mas é o arness que decide então compactar. Nunca deixe que a decisão modelo reescrever ele mesmo o histórico; conserva as decisões e artefatos duradouros em `HANDOFF.md` / `MIGRATION_STATE.md`.
- **Presuposto de selecção** : se um elemento de contexto não alterar nenhuma decisão do passo actual, não pertence à janela. Medir periodicamente a parte dos tokens que realmente influenciaram a saída (taxa de 'cache' hit, redundância dos ficheiros injetados): uma janela grande não é uma desculpa para um contexto não filtrado.

>
> **Qwen Code faz com que este orçamento seja agora observável.** As versões 0.23.x mostram a parte do contexto consumido pelo

> Estas práticas respondem aos quatro modos de falha mencionados na taxonomia de referência: *context vensoning*

#### Árvore de decisão: continuar vs handoff + sessão fresca vs `/compact`

O erro mais caro em créditos é continuar uma sessão contaminada. Aqui está a árvore de decisão a aplicar todos os ~15 interação ou quanto um sintoma de context rot:

```text
Session en cours
│
├─ L'agent répète une hypothèse déjà réfutée ou accumule les erreurs ?
│  └─ OUI → STOP → HANDOFF.md vérifié → nouvelle session
│             (ne PAS changer seulement de modèle dans la conversation polluée)
│
├─ Le contexte contient > 50 % de tokens non décisionnels
│  (logs bruts, rg massif, anciennes versions du diff) ?
│  └─ OUI → écrire HANDOFF.md :
│             objectif, contraintes, plan, décisions, artefacts,
│             diff courant, preuves, erreurs non résolues, prochaine action
│           → relire le handoff
│           → nouvelle session avec ce working set minimal
│
├─ La tâche a changé de nature ?
│  (bugfix → refactor, feature → migration)
│  └─ OUI → nouveau cadrage complet (Étape 0) + nouvelle session
│
├─ Le modèle utilise encore correctement les invariants et non-objectifs ?
│  └─ NON → ré-injecter la charte si le contexte reste sain ;
│           sinon handoff + nouvelle session
│
└─ Aucune condition ci-dessus → continuer
```

`/compact` torna-se o **plan B**, reservado aos casos em que a superfície impõe conservar a sessão. Antes de usar, faça com que produza e depois relee um handoff estruturado; depois de compacção, verifica explicitamente que os invariantes, decisões, artefatos e erros abertos sobreviveram. Se falta um detalhe crítico, abandona a sessão compactada.

Regra métrica: se o rácio (tokens na janela) / (tokens realmente citados ou utilizados na 3 Últimas respostas) supera 5:1, a sessão está sobrepeso. O defeito é **handoff + sessão fresca**, não mais compressão.

## Exemplo: estruturar uma petição escondida na Scala 3

A disciplina da secção 4 (estático na parte superior, dinâmica na parte inferior) traduz-se diretamente na construção da consulta. `cache_control` cobram-se ~5 à 10 % da tarifa input a partir do segundo convite (5 % de Sonnet 5.5 e Opus 5.5) Sempre que for byte para byte idênticos entre as chamadas:

```scala
import io.circe.Json
import io.circe.syntax.*

object CacheablePrompt:

  // STATIQUE — chargé une fois au démarrage, jamais reconstruit dynamiquement :
  // toute interpolation (timestamp, compteur...) dans ces blocs casse le cache.
  def systemBlocks(agentsMd: String, scalaRules: String): Json =
    Json.arr(
      Json.obj(
        "type"          -> "text".asJson,
        "text"          -> agentsMd.asJson,
        "cache_control" -> Json.obj("type" -> "ephemeral".asJson)
      ),
      Json.obj(
        "type"          -> "text".asJson,
        "text"          -> scalaRules.asJson,
        "cache_control" -> Json.obj("type" -> "ephemeral".asJson)
      )
    )

  // DYNAMIQUE — change à chaque itération, va dans messages, jamais dans les blocs cachés
  def userMessage(diff: String, compileErrors: String): Json =
    Json.obj(
      "role"    -> "user".asJson,
      "content" -> s"Diff courant :\n$diff\n\nErreurs :\n$compileErrors".asJson
    )

  def request(agentsMd: String, scalaRules: String, diff: String, errors: String): Json =
    Json.obj(
      "model"      -> "claude-sonnet-5-5".asJson,
      "max_tokens" -> 4096.asJson,
      "system"     -> systemBlocks(agentsMd, scalaRules),
      "messages"   -> Json.arr(userMessage(diff, errors))
    )
```

Verifica a 'cache' hit na resposta (`usage.cache_read_input_tokens > 0`) e loggelo: uma taxa de 'cache' hit que quase sempre se despoleta indica um cabeçalho de prompt que se torna instável. 4 da secção
